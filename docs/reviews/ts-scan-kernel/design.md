# ts-scan-kernel — TypeScript 가드의 스캔 커널

**날짜**: 2026-08-25 · **브랜치**: cli-deepening · **스캔 근거**: `/tmp/.../architecture-review-20260825-110611.html`(후보 15건)

## 1. 선택과 기각

### 선택: A3 — TypeScript 가드에는 스캔 커널이 없다

셸에는 `scripts/lib/scan-floor.sh`(코드 25줄 · 노출 함수 4개 · 소비자 15곳)가 실재하는 깊은 모듈로 있고
**그 축의 드리프트는 0**이다. TypeScript 쪽에는 같은 커널이 없어 가드 7개가 규약을 **주석으로 재현**하며,
그중 **4개가 어긋났다**. 이 후보만이 현재 트리에 살아 있는 결함을 지목하고, 설계 리스크가 낮다.
새 인터페이스를 발명하는 것이 아니라 **같은 레포에서 이미 15개 소비자에게 통한 커널**을 언어 경계 너머로
옮기는 일이기 때문이다.

### 이긴 후보들 (같은 스캔에서 `Strong`으로 올라온 것)

| 후보 | 왜 이번이 아닌가 |
|---|---|
| B1 push 메트릭 발행 계약 | 레버리지는 가장 크지만(생산자 6곳 + 강제 없던 4곳 편입) 표면이 넓다. 다음 pass 1순위. |
| C1 bump 소유권 증명 계약 | 물증이 가장 선명하다(45줄 소스 스크레이퍼). 범위도 작다. 다음 pass 2순위. |
| C2 배포 핀 레인 | 분기 7곳이 5파일에 흩어짐. 값은 크나 A3보다 설계 자유도가 높아 리스크가 크다. |
| C3 bump 실행기 관측 계층 | 1909줄 · export 0. 값이 크지만 한 번에 꺼내면 위험해 별도 pass가 필요하다. |
| A1 가드 등록 9자리 · A2 검출기 하네스 | 같은 계층이라 A3 이후가 자연스럽다. A2는 A3와 형태가 가장 가깝다. |

### 삭제 테스트로 기각한 것 (재탐사 방지)

- **셸/TS 분할 해소** — 분할은 **진짜 seam**이다(대상·열거·검출 세 축이 일관되게 갈림). 합치면 복잡성이 커진다.
- **`check-alert-rules.ts` 쪼개기** — 얕지 않다. 판정 5종이 공유 판독기 187줄 위에 선 **깊은** 모듈이다.
- **프로비저너 골격 공용화** — 도구당 ~5줄 관용구. 지우면 관용구가 재현될 뿐이다.

## 2. 진단 — 실측

셸 커널의 규약은 두 가지다. **바닥값 실패 시 신호를 억제**하고, **바닥값 통과 시 신호를 자동 방출**한다.
TS는 콜사이트가 그 순서를 손으로 맞춰야 하고, 맞춰야 하는 곳마다 갈렸다.

| 가드 | 바닥값 | SCAN 신호 | 판정 |
|---|---|---|---|
| `check-resource-limits` | `MIN_SCAN=10` (:110) | 바닥값 → 신호(:118) → 위반 | 정확 |
| `check-guard-authority` | `--min-scan` (:321) | 바닥값 → 신호(:347) → 위반 | 정확 (`--json`이면 억제) |
| `check-image-ownership` | `--min-refs` (:379) | 바닥값 → 신호(:394) → 위반 | 정확 |
| `check-workflow-readiness` | `minWorkflows`(:257) · `minDeclarations`(:418) | **선언 바닥값 실패해도 신호 방출**(:421) | 어긋남 |
| `check-disk-caps` | `MIN_FLAGS`(:113) | **위반 실행에서 신호 0건**(:119 exit이 :125 신호보다 앞) | 어긋남 |
| `check-alert-rules` | 4종(:660 · :999 · :1004 · :1008) | **3개가 신호(:986~992) → 바닥값 역순** | 어긋남 |
| `check-ci-parity` | `MIN_STEPS=19`(:146) | **신호 자체가 없음** | 누락 |

### 실증

- `check-disk-caps`: 위반 매니페스트 1건짜리 픽스처 레포에서 `bun tools/check-disk-caps.ts` → rc=1, `^SCAN:` 매치 **0건**.
- `check-alert-rules:983`의 주석이 규약을 **정확히** 적어 뒀다 — "면제는 바닥값 실패 경로뿐". 그 아래 코드는 반대다.
- `check-resource-limits:115-117`이 원인을 진술한다 — "셸 가드는 커널이 바닥값 시점에 내므로 자동으로 이 위치인데,
  **TS는 콜사이트라 순서를 손으로 맞춰야 한다**."

### 어휘 드리프트 (부수 발견 — 이 티켓의 범위 밖)

같은 이름 `fail`이 정반대로 동작한다. `check-guard-authority:304`는 `never`를 반환하며 즉시 `process.exit(1)`,
`check-ci-parity:61`은 `(m) => errors.push(m)`이다. 후자는 `check-disk-caps`가 어긋난 그 구조와 같다.
**통일은 별도 티켓**으로 다룬다(이번엔 바닥값만 커널로 옮긴다).

## 3. 커널 설계

**자리**: `tools/lib/scan-floor.ts` — 셸과 **파일 이름을 맞춘다**. 두 커널이 한 규약의 두 adapter라는 사실이
디렉토리만 봐도 읽혀야 한다. `tools/lib/cli.ts`(64줄, 플래그 파싱 + 종료코드 관용구)에 섞지 않는다.

### 표면 (함수 3개)

```
scanFloor(label, got, min, opts?)   바닥값 검사 → 실패: ScanError throw / 통과: 신호 방출
scanSignal(label, n, opts?)         신호만 (바닥값이 걸리지 않은 카운트 자리)
parseFloor(raw, source)             raw 문자열 → 바닥값 수, 아니면 ScanError throw   ← 게이트 r2
opts = { quiet?: boolean, hint?: string }
ScanError.exitCode                  권고 종료코드 — 열거 붕괴 1 · 임계값 입력 오류 2
```

셋째는 셸에서 온 것이 아니라 **게이트 r2가 연 축**이다(아래 "임계값" 절). 셸에는 이 병이 없다 —
셸 콜사이트는 `${VAR:-기본값}`으로 문자열을 그대로 넘기고 `[ "$got" -lt "$min" ]`이 수가 아닌 값에
**에러를 낸다**. TypeScript의 `Number("")===0`과 `n < NaN === false`가 이 자리를 조용하게 만든다.

- **마커 형태 `SCAN: <라벨>: <n>`는 셸과 한 글자도 다르지 않다.** 함수 이름만 camelCase로 옮긴다.
  사람이 두 adapter의 출력을 나란히 읽을 수 있어야 하고, 게이트의 파싱 정규식도 하나다.
- **실패는 예외로 나간다 — 커널은 종료하지 않는다** (코드리뷰 H1으로 초안을 뒤집었다).
  초안은 "커널이 `process.exit`을 친다"였고 셸의 `|| exit N`과의 동형을 논거로 삼았다. 그런데 셸 커널은
  `scripts/lib/`에 있고 TypeScript `tools/lib/`는 **정반대 규율**을 네 곳에 명시한다 —
  `tools/README.md`("콜사이트가 정책 소유") · `image-pin.ts`("process.exit는 전부 콜사이트 소유") ·
  `repo-walk.ts` · `sealed-contract.ts`. 그대로 갔다면 `scan-floor.ts`가 그 규율을 깨는 **유일한 lib**이
  됐을 것이고, 자기 주석에 "종료코드는 콜사이트가 소유한다"고 적으며 정반대를 구현하는 상태였다.
  → `ScanError`를 던지고 **콜사이트가 잡아 종료한다**. 에러가 권고 코드를 실어 보내므로 콜사이트가
  두 실패를 구별할 수 있고(붕괴 1 · 입력 오류 2), 셸이 `exit 1`/`exit 2`로 갈리듯 덮어쓸 수도 있다.
  `check-disk-caps.ts`가 `walkManifests` 실패를 처리하던 형태와 같아서 콜사이트 관용구도 새것이 아니다.
- **그래도 콜사이트가 두 사고를 합칠 수 없어야 한다.** boolean 반환은 무시할 수 있지만 예외는 명시적으로
  잡아야 하고, `catch` 블록은 `bad.push` 한 줄과 달리 눈에 띈다. 회귀 증인은 **"커널이 종료하지 않는다"를
  정적으로 단언하는 테스트**다(뮤테이션 실측: 커널이 종료를 도로 가져가면 4건이 red).
- **`quiet`는 stdout 마커만 삼킨다.** 바닥값 검사와 stderr 진단은 그대로 수행한다.
  `check-guard-authority`가 `--json` 모드에서 stdout을 JSON으로 쓰기 때문에 필요하다. 억제는 출력 채널의
  성질이지 판정의 성질이 아니므로, 커널이 출력을 소유한 이상 억제도 커널이 안다.

### 이식하지 않는 것 (근거를 커널 주석에 남긴다)

| 셸 함수 | 비이식 근거 |
|---|---|
| `scan_enumerate` | 프로세스 치환이 열거자 rc를 삼키는 병이 TS에 없다. 열거는 `tools/lib/repo-walk.ts`가 소유한다. |
| `scan_count` | `grep -c .`가 0건일 때 rc=1이 되는 함정이 TS에 없다. `.length`다. |

동형성은 **함수 개수가 아니라 규약의 의미**에서 지킨다. 병이 없는 자리에 함수를 만들면 그 자체가 얕은 모듈이다.

### 임계값은 커널이 고르지 않는다 — 그러나 수인지는 판정한다

주입 방식이 셋으로 갈린다(상수 `MIN_SCAN=30` · 플래그 `--min-scan` · 환경변수 `DISK_CAP_MIN_FLAGS`).
값의 **선택**은 콜사이트가 소유한다. 셸 커널 주석의 결정을 그대로 물려받는다 — *"바닥값 수치는 소비자가
소유한다. 열거자는 '글롭이 깨져 0건'과 '정당하게 0건'을 구별할 도메인 지식이 없다."* 주입 방식 통일은
이 티켓 밖이다.

**그러나 값이 수인지는 커널이 판정한다** (게이트 r1 F2 · Accept). 지금은 그렇지 않고, 그 결과가 실측된다:

```
DISK_CAP_MIN_FLAGS=abc bun tools/check-disk-caps.ts
  → SCAN: check-disk-caps:caps: 2 · rc=0
bun tools/check-guard-authority.ts --min-scan abc
  → SCAN: …:guards: 42 · SCAN: …:venues: 297 · rc=0
```

`Number("abc")`가 `NaN`이고 `n < NaN`은 항상 false라 **바닥값이 통째로 꺼진 채 초록**이 된다.
오타 하나가 이 커널이 없애려는 실패 클래스를 그대로 되살린다.

**이 레포는 같은 클래스를 이미 한 번 밟았다.** `positiveInt(raw, flag)`가 그 처방인데,
`check-image-ownership.ts:234`와 `check-workflow-readiness.ts:613`에 **바이트 동일하게 복제**되어 있고
후자의 주석이 근거를 적어 뒀다 — *"`Number("")===0`이라 빈 값이 바닥값을 조용히 끄는 자리다
(같은 클래스의 실측 버그가 있었다)."* 처방이 둘에만 손으로 적용되고 나머지 둘(`check-disk-caps:36` env ·
`check-guard-authority:317` flag)은 raw `Number(...)`로 남았다. **검출기 하네스 복제와 같은 형태다.**

따라서 유효성 판정을 커널 계약에 넣고, 복제 2벌을 흡수한다.
**다만 숫자를 검증하는 것만으로는 부족하다** (게이트 r2 · Accept).

`Number("")`는 `0`이다. 커널이 `number`만 받으면 그 `0`은 "유한한 안전 정수이며 음수 아님"을 만족해
그대로 통과하고, 커널은 **의도적 0과 빈 입력에서 온 0을 원리적으로 구별할 수 없다**. 0을 금지해서
피할 수도 없다 — 0은 정당한 바닥값이다(셸 선례: `check-app-deploy.sh:121`의 `APP_DEPLOY_MIN_SCAN:-0`,
`check-image-pins.sh:33`의 "앱이 0개인 동안은 레인2 열거 0건이 정당해 붕괴와 구별되지 않는다").

그리고 숫자 검증만 넣고 `positiveInt`를 걷어내면 **회귀가 난다**. 실측:

```
bun tools/check-image-ownership.ts --min-refs ""
  → "--min-refs는 음이 아닌 정수여야 한다(받은 값: '')" · 비-0    ← 지금은 거부한다
bun tools/check-guard-authority.ts --min-scan ""
  → SCAN: …:guards: 42 · SCAN: …:venues: 297                      ← 미적용이라 통과한다
```

F2를 고치려는 수정이 **현재 정확한 두 곳에 같은 클래스의 구멍을 새로 여는** 셈이다. 따라서 검증은
coercion **앞**에 세운다.

- **`parseFloor(raw, source)`가 세 번째 함수다.** `string | undefined`를 받아 `/^\d+$/`로 판정하고,
  아니면 진단 + **exit 2**, 통과하면 `number`를 돌려준다. `positiveInt`의 수렴형이며, 그 함수의
  호출처 3곳(`--min-workflows` · `--min-declarations` · `--min-refs`)이 전부 바닥값 주입이라
  범용 정수 파서가 아니라 **바닥값 파서**다.
- **주입 지점 넷을 모두 이 경로로 모은다** — `check-disk-caps:36`(env) · `check-guard-authority:317`(flag) ·
  `check-image-ownership:369`(flag) · `check-workflow-readiness:643-644`(flag×2).
- **명시적 0은 통과시킨다.** `/^\d+$/`가 `"0"`을 받고 `""`를 거부하므로 두 경우가 갈린다.
- `scanFloor` 안의 숫자 검증(유한·안전 정수·음수 아님)은 **안전망으로 남긴다.** 상수로 주입되는 자리
  (`MIN_SCAN = 30`)는 파서를 거치지 않으므로 그 경로를 덮는 것이 필요하다.
- 거부가 싣는 권고 종료코드는 **2**다(바닥값 실패의 1과 구별). "바닥값이 수가 아니다"는 사용법 오류이고
  "열거가 붕괴했다"와 다른 사고다. `positiveInt`가 이미 exit 2를 쓰고 `cli.ts:57`이 같은 규약을 적었다.
- **순서 제약**: 기존 `positiveInt` 2벌을 제거하기 **전에** 빈 문자열이 exit 2를 내는 테스트가 green이어야
  한다. 뒤집으면 회귀가 무증인 상태로 들어간다.
- 테스트는 잘못된 입력으로 연다(`abc` · 빈 문자열 · 음수 · 소수) — 그리고 **`"0"`은 통과해야 한다**.

이것은 "임계값은 콜사이트가 소유한다"와 충돌하지 않는다. 값을 **고르는** 것은 콜사이트이고, 그 값이
**수인지**는 판정 기계의 일부다. 이 구별이 없으면 커널은 자기 정의("판정 기계만 공유한다")를 지키지 못한다.

### 두 리터럴을 감수하는 근거

`SCAN: <라벨>: <n>` 형태가 `scan-floor.sh:61`과 새 TS 커널 두 곳에 리터럴로 남는다. 같은 스캔에서 C1이
문제 삼은 "생산자와 검증자가 같은 문자열을 각자 든다"와 형태가 같으므로, **왜 여기서는 괜찮은지**를
커널 주석에 적어야 한다. C1이 위험한 이유는 두 리터럴의 일치를 아무도 실행으로 확인하지 않아 소스
스크레이퍼가 필요했다는 것이다. 여기는 반대다. `test_scan-floor.bats`가 셸 adapter 6종(:167~180)과
TS adapter 전량(:191~208)을 **실제로 실행해서** 같은 정규식으로 방출을 파싱한다. 한쪽이 형태를 바꾸면
그 정규식이 못 잡아 즉시 red다. 실행 대조는 리터럴 대조보다 강하다.

## 4. 소비자 이행 — 7개 전부

도메인별로 **(바닥값 → 신호)를 한 몸으로** 순차 호출한다. 첫 도메인이 붕괴하면 뒤 도메인의 신호는
나가지 않는다. 셸이 이미 그렇게 동작한다(`check-gh-secret-coverage.sh`가 77·136 두 도메인을 순차로
부르고 첫 실패에서 exit 2).

바닥값을 전부 먼저 검사하고 신호를 몰아 내는 방식은 **배제한다**. 둘을 떼어 놓는 순간 그 사이에 무엇이든
낄 수 있고, `check-disk-caps`에 낀 것이 바로 위반 exit이었다.

| 가드 | 라벨 | 작업 |
|---|---|---|
| `check-disk-caps` | `caps` | 바닥값을 `bad` 배열에서 분리해 커널로 |
| `check-alert-rules` | `rules` · `denylist` · `supply` · `supply-refs` | 신호 4개 몰아내기를 해체, 도메인별 순차로 재배치 |
| `check-ci-parity` | `check-ci-parity` **(신규)** | 바닥값을 `errors` 수집에서 분리. 나머지 오류 수집 관용구는 그대로. 도메인이 하나라 접미사를 붙이지 않는다(커널 규약) |
| `check-workflow-readiness` | `workflows` · `declarations` · `accounted` | `checkStatic` 반환 계약 변경 (아래) |
| `check-resource-limits` | (1개) | 치환 |
| `check-guard-authority` | `guards` · `venues` | 치환 + `quiet` |
| `check-image-ownership` | `refs` | 치환 |

### 세부 판단 3건

**`check-ci-parity`의 신호 신규 추가.** 바닥값은 있는데 신호가 없어 네 번째 변종이었다. 이것을 빼면
커널 주석이 인정한 "커버리지는 완전하지 않다"가 계속 참으로 남는다. 바닥값만 즉시 죽는 것이 옳다.
바닥값 실패는 "이 실행은 아무것도 측정하지 않았다"는 뜻이므로 그 뒤에 모인 오류는 0건 검사에서 나온
것이라 함께 보고하면 잘못된 그림을 준다. **커널에 "수집 모드"를 만들지 않는다** — 그것은
`check-disk-caps`가 저지른 일을 커널이 승인한 경로로 만드는 것이다.

**`check-guard-authority`의 `venues`.** 바닥값이 `authoritativeVenues.length === 0`에 걸리는데 신호는
`venues.length`를 낸다. **검사한 수와 보고한 수가 다른 유일한 자리**다. `scanSignal`로 두고 0건 검사는
별도 `fail()`로 남긴다. 신호 대상을 바꾸면 게이트의 런타임 방출 **값**이 바뀌는데, 이 티켓은 순서와
억제를 고치는 것이지 무엇을 세는지를 바꾸는 것이 아니다. 셸도 같은 자리를 갖는다
(`check-argocd-revision.sh:106`이 `scan_signal`을 직접 부른다).

**`check-workflow-readiness`의 구조 변경.** 7개 중 이것만 제어 흐름이 바뀐다. 바닥값 두 개를 서로 다르게
처리한다 — 워크플로 열거(:257)는 `bad.push` 후 **조기 반환**(:259)이라 신호가 안 나가고(규약 맞음),
선언(:418)은 `bad.push`만 하고 신호는 무조건 나간다(규약 어긋남). `checkStatic`이 `string[]`을 반환하고
실제 종료는 상위 :650에서 일어나므로, 커널이 exit하면 반환 계약이 달라진다. 조기 반환이 지금 손으로
구현한 것을 커널이 흡수한다. `accounted`는 `--workflow` 런타임 모드에서만 나오는 모드 의존 콜사이트다.

## 5. 게이트 전환 — 빠뜨리면 안 되는 마지막 티켓

`tests/gates/test_scan-floor.bats`의 핵심 단언은 **정적 콜사이트 집합 == 런타임 방출 집합**(:214)이다.
정적 축은 소스 grep(`^[^/]*SCAN: `, :191)으로 얻는다. 콜사이트를 하나라도 커널로 바꾸면 그 라벨이 정적
grep에서 사라지고 런타임에는 남아 **집합이 어긋난다**. 소비자를 하나씩 옮기는 방식은 중간 상태가 전부 red다.

전환 전략은 **양쪽 인식 후 축소**다.

1. 게이트의 정적 grep을 옛 형태(`console.log(\`SCAN:`)와 새 형태(`scanFloor(`·`scanSignal(`) **둘 다**
   인식하도록 확장한다. 이후 각 이행 티켓이 독립적으로 green이다.
2. 소비자를 티켓 단위로 옮긴다.
3. **마지막 티켓에서 옛 형태 인식을 제거하고, 직접 생산자를 거부하는 가드를 추가한다.**

### 인식을 거두는 것만으로는 문이 닫히지 않는다 (게이트 r1 F1 · Accept)

3번의 앞 절반만 하면 우회로가 열린 채 남는다. **정적 집합과 런타임 파일 목록이 같은 grep에서 파생되기
때문이다**(`static`은 :191, `files`는 :197, 패턴이 같다). 한 가드가 직접 출력으로 되돌아가면

- 정적 집합에서 그 라벨이 빠지고,
- `files`에도 그 파일이 안 잡혀 **실행되지 않으므로** 런타임 집합에서도 빠진다.

양쪽이 함께 줄어 **등식 `[ "$static" = "$runtime" ]`은 그대로 성립한다.** 남은 방어선은 정적 집합
바닥값 하나인데, 이 문서가 "바닥값은 래칫이 아니므로 여유를 둔다"고 정한 그 여유가 정확히 한 건의
손실을 덮는다. 새로 추가된 직접 생산자도 같은 이유로 보이지 않는다. **커널을 도입하고도 커널 우회
드리프트가 그대로 남는다.**

그래서 **거부**가 필요하다. 인식 제거는 "안 본다"이고, 필요한 것은 "있으면 red"다.

- `tools/**/*.ts`에서 주석이 아닌 줄이 `SCAN: `를 **직접 출력**하면 실패한다. 이행 후 기대값은 0건이다.
- **커널 자신은 면제 대상이다.** 면제 판정을 주석 판정보다 **뒤에** 둔다 — 이 레포의 함정 원장에
  "면제 판정이 주석보다 먼저 돌면 규약을 *설명한* 파일이 그 규약에서 면제된다 — 가드 자신부터"가 있다.
  면제는 커널 **파일 경로 하나**로 좁히고, 그 목록을 넓히지 않는다.
- 이 가드 자신도 **열거 바닥값**을 갖는다. 검사한 `.ts` 파일 수가 바닥값 미만이면 red다.
  자기가 붕괴한 채 "직접 생산자 0건"을 보고하는 것이 이 문서가 다루는 그 병이다.

### 채택하지 않은 두 권고 (r1 F1)

- **AST 기반 콜사이트 발견** — 검출 메커니즘을 정교하게 바꿀 뿐 위 구멍을 막지 못한다. 구멍은 "우회한
  가드가 양쪽 집합에서 동시에 사라진다"는 것이고, 그것은 발견 방식이 아니라 **거부 축의 부재**다.
  범위도 크게 넓어진다.
- **여유 없는 정확한 커버리지 기대값** — 이 레포가 명시적으로 기각한 패턴이다. 커널 주석이 근거와
  실측을 함께 적었다 — *"여기에 건수를 적지 않는다. 아무도 대조하지 않는 손 관리 수치는 반드시
  드리프트한다 — 실측한 적이 있다: 주석은 '11종/27종', 실제는 13종/31종."* 거부 축이 서면 바닥값이
  여유를 유지해도 무방하다.

### 함께 손대는 것

- **정적 집합 바닥값**(`[ "$n" -ge 6 ]`, :195)을 새 라벨 수에 맞춰 조정한다. 이 바닥값은 이미 있고
  ("콜사이트가 통째로 사라지면 정적·런타임이 함께 줄어 등식이 유지된다 — 적대 검토가 실측한 구멍"),
  `check-ci-parity` 신호 추가로 라벨 수가 늘어난다. **바닥값은 래칫이 아니므로** 여유를 둔다.
- **`files` 열거**(`grep -lE`, :197)도 같은 패턴 확장이 필요하다. `[ -n "$files" ]`가 뒤를 받친다.
- 이 게이트는 원래 하드코딩 목록(3종)이었는데 실제 방출은 5종이었고 그래서 파생으로 고쳤다
  (:186 주석, "하드코딩 소비처 목록은 자기 자신에게만 정확하다"). **다시 손으로 적지 않는다.**

### 커널 테스트 — 셸 4개를 전부 이식

`tests/gates/test_scan-floor.bats`에 TS 섹션을 추가한다(새 파일을 만들지 않는다 — 두 adapter가 한 파일에서
나란히 보여야 하고, 다른 파일에 살면 다음 사람이 한쪽만 고칠 여지가 생긴다).

| 이식할 셸 테스트 | TS 대응 |
|---|---|
| `scan_signal emits the marker in the agreed shape` | `scanSignal` 형태 |
| `scan_floor emits the scan marker when it passes` | 통과 시 방출 |
| `scan_floor does NOT emit the scan marker when it fails` | **드리프트 ①②를 잡는 테스트** |
| `the scan marker never carries the skip marker (exclusive channels)` | SKIP/SCAN 배타 채널 |

넷째는 vacuous 방지 장치를 품고 있다 — 마커 존재를 **먼저** 단언한다. 그것이 없으면 "SKIP이 없다"가
마커가 아예 없어도 참이 되어 테스트가 자기 자신 vacuous가 된다(적대 검토 지목). 이식할 때 그 장치를 함께
옮긴다.

셸 테스트가 `run bash -c '. "$1"; scan_floor demo 0 5'` 형태로 라이브러리를 source해 함수를 직접 부르므로,
TS는 `run bun -e '…'`로 커널을 import해 부르고 종료코드를 본다. `@test` 이름은 **영어**로 쓴다
(디렉토리 단위 실행에서 한글 이름이 침묵 스킵되는 검증된 버그).

`scripts/check-bats-accounting.sh`가 bats 파일 소재를 회계하므로, 기존 파일에 추가하는 이 방식이 원장을
건드리지 않는지 이행 시 확인한다.

## 6. 도메인 어휘 — `CONTEXT.md`

「가드 규약」 절을 신설하고 두 항목을 추가한다. 둘은 짝이라 하나만 넣으면 반쪽이다.

- **스캔 신호 (scan signal)**: `SCAN: <라벨>: <n>` 형태의 실행 관측 마커. 가드가 CI에서 **돈다는 사실**과
  그 호출이 **실제 도메인에 닿았다는 사실**을 가르는 유일한 기계 입력이다. `SKIP:`과 배타 채널이다.
- **열거 바닥값 (enumeration floor)**: 열거가 붕괴해 0건을 검사하고 초록이 되는 것을 막는 하한.
  **수치는 콜사이트가 소유한다** — 커널은 "글롭이 깨져 0건"과 "정당하게 0건"을 구별할 도메인 지식이 없다.

### "레인" 충돌 해소

가드 계층이 쓰던 "셸 레인/TS 레인"을 **adapter**로 바꾼다(`test_scan-floor.bats:188` 주석 한 줄).
CONTEXT.md의 **레인**은 배포 핀의 표현 갈래(apps 레인 · 베스포크 레인)에 뿌리내린 용어이고 `_Avoid_`로
경계까지 그어 뒀다. 「가드 규약」 절에 `_Avoid_: 레인(배포 핀 도메인 전용)`을 명시한다.

이 교정이 설계의 값도 정확히 설명한다. 지금은 adapter가 하나뿐이라 seam이 **가설**이고, TS 커널이 생기면
둘이 되어 **진짜 seam**이 된다.

## 7. 티켓 분할과 블로킹 엣지

```
T1 (tracer bullet)  커널(scanFloor·scanSignal·parseFloor) + 이식 테스트 4개 + 임계값 입력 테스트
                    + 게이트 양쪽 인식 확장 + check-disk-caps
      ↓ blocks
T2  정확한 3개 치환 (check-resource-limits · check-guard-authority · check-image-ownership)
T3  check-alert-rules (라벨 4개 순서 재배치)
T4  check-ci-parity (신호 신규 + 바닥값 분리)
T5  check-workflow-readiness (반환 계약 변경 · 모드 의존 콜사이트)
      ↓ 위 전부 blocks
T6  게이트에서 옛 형태 인식 제거 + **직접 생산자 거부 가드** + 정적 바닥값 확정
T7  "레인"→adapter 교정 (test_scan-floor.bats:188 주석)   (T6과 함께 하는 편이 자연스럽다)
    ※ CONTEXT.md 「가드 규약」 절은 이 설계 커밋에서 선행 완료했다 — 용어가 설계보다 늦으면
      티켓 본문이 교정 전 어휘로 쓰인다.
```

**T1이 `check-disk-caps`를 포함하는 이유.** tracer bullet의 목적은 얇은 것을 먼저 하는 것이 아니라
**위험한 가정을 먼저 검증하는 것**이다. 이 설계의 가장 위험한 가정은 "커널이 exit을 소유하면 콜사이트가
바닥값을 다른 오류와 합칠 수 없다"이고, `check-disk-caps`가 정확히 그 합침을 저지른 파일이다. 거기서
커널이 통하면 나머지는 따라온다. `check-resource-limits`가 더 얇지만 이미 정확한 코드의 순수 치환이라
**아무것도 증명하지 않는다**.

**T5를 떼는 이유.** 나머지 여섯은 호출 형태만 바뀌는 치환인데 이것만 제어 흐름이 바뀐다. 성격이 다른
변경을 같은 티켓에 넣으면 리뷰가 쉬운 쪽에 눈을 빼앗긴다. 게다가 게이트가 이 가드를 **두 번 실행**해서
덮으므로(`:208`이 `--workflow bump-poll.yaml`로 따로 부른다) 회귀 표면이 다르다.

**T6은 협상 대상이 아니다.** 5절 참조. 그리고 T6의 값은 인식 제거가 아니라 **거부 가드**에 있다.
r1 F1이 보인 대로, 인식만 거두면 우회한 가드가 정적·런타임 집합에서 동시에 사라져 등식이 유지된다.

**T1의 커널이 유효성 판정을 함께 담는다.** r1 F2가 요구한 것이고, 복제된 `positiveInt` 2벌을 흡수하며
미적용 2곳을 덮는다. 그중 하나가 T1의 대상인 `check-disk-caps`이므로 첫 슬라이스에서 함께 증명된다.

**`positiveInt` 제거에는 순서가 걸린다**(r2). 그 2벌은 `check-image-ownership`(T2)과
`check-workflow-readiness`(T5)에 있고 **지금 빈 입력을 실제로 거부한다**. T1의 `parseFloor`와
빈 문자열 exit 2 테스트가 green이 되기 전에 제거하면 회귀가 무증인 상태로 들어간다. T1이 T2~T5를
이미 blocks하므로 제약은 자연히 만족되지만, T2와 T5의 **수용 조건에 명시한다**.

## 8. 살아남는 것과 사라지는 것

### 살아남는 테스트

- `test_scan-floor.bats`의 셸 adapter 단위 테스트 4개와 셸 콜사이트 증인 6종(:167~180) — 손대지 않는다.
- 정적 == 런타임 집합 대조(:214) — 파싱 패턴만 바뀌고 단언은 그대로다.
- `--json` 모드 전용 단언(:218) — `quiet` 옵션이 그 성질을 보존한다.
- 모드 의존 콜사이트를 실행으로 덮는 방식(:208) — 제외 목록을 만들지 않는다는 원칙 그대로다.
- 각 가드의 도메인 테스트 전량 — 이 티켓은 판정을 바꾸지 않는다.

### 사라지는 것

- 7개 가드에 흩어진 "순서를 손으로 맞춰라"는 주석 — 순서가 함수 안으로 들어가면 설명할 것이 없다.
- 드리프트 4건(신호 억제 2건 · 신호 누락 1건 · 신호 부재 1건).

# 05 — NUC 배선과 전체 파일럿 수용

Status: needs-info
Blocked by: Q13, 01, 02, 03, 04
Design: [수용 기준](../design.md#9-수용-기준), [사용자 작업](../design.md#10-구현과-사용자-작업)

## 결과

NUC의 systemd 작업이 모든 기존 장애 알림을 수집하고, 구독 Codex의 진단과 검증한 Draft PR을
전달한다. 동작·권한·실패 수용 증거를 확보한 뒤 실제 알림 14일 관찰을 시작한다.

## 구현 범위

1. 호스트 기존 관례에 맞춰 전용 실행/수집/게시 역할, systemd unit, durable 경로와
   보존 정리를 구성한다. host-config의 설치와 enable을 구분하고 정확한 중지·롤백 절차를 준비한다.
2. Codex 로그인, fork/App 설치, healthchecks read-only 키 등 사람의 작업은 설정 템플릿과
   검증기를 먼저 준비한 뒤 안내한다. 시크릿은 채팅으로 받지 않는다. 실제 역할 권한을 확인한다.
3. 재부팅·worker 사망·query 불능·auth 만료·quota 소진·timeout/OOM·게시 응답 유실에서
   큐/예산/기존 통지가 보존되는지 확인한다. NUC 자원·디스크·상태 신선도를 측정한다.
4. 최소 12개 고정 사례로 원인 근거·반증·보류·수정 필요성과 모든 생산자 도달을 평가한다.
   정답 문서는 모델 입력에서 분리하고, 정제/권한 시험과 진단 품질 평가를 따로 기록한다.
5. 모든 생산자와 권한 수용 후 실제 알림 파일럿을 시작한다. 14일 동안 운영자의 확인 시간·
   오진·보류·검토 비용·확인된 사용량을 기록한다. 사건 수가 부족하면 효과 입증은 미완료다.

문서·새 도구·unit·정책은 해당 로스터와 gate에 편입한다. 메모리 원장 cap이나 기존 writer
권한을 AIOps 편의를 위해 자동 확대하지 않는다. 실제 자원 부족은 측정 근거와 조정안으로 다룬다.

단계별 상한은 실제 NUC에서 수집 정지·살아 있는 worker 정지·검증 무한 대기·출력 폭주·
TERM 무시 자식으로 확인한다. cgroup 종료 후에만 lease가 풀리고 다음 사건이 진행돼야 한다.
정리 확인 불능은 새 실행 차단과 통지로 드러나야 한다. GHA 정상 복귀는 Telegram 미발송 상태의
실제 검사 결과 artifact로 확인하고, 고정 검사는 기준 정상·후보만 위반인 사본으로 검증한다.
원장 대조군에는 후보 행과 예산 메타데이터를 함께 높인 경우를 포함한다. 기준 상한으로는
실패하고 후보 상한 기준의 결과는 분리돼야 하며, 기준 상한을 읽지 못하면 후보 값으로 대체하지 않는다.

plan r1 a4는 사용자 선택으로 실제 관찰 시작 전까지 보류했다. 담당은 이 티켓이며, 관찰을
켜기 전에 최소 사건 수·생산자 범위, 기존 수동 대응과 비교할 시간의 측정 방법, 성공/실패/
평가 부족 판정을 문서화한다. 기존 12개 고정 사례의 진단 수용 조건은 계속 시작 전에 충족한다.
숫자를 미리 정하지 않았다는 이유로 코드 구현을 막지 않으며, 14일 경과만으로 효과를 입증하지 않는다.

## 완료 증거

01~04의 로컬 검사, 실제 NUC 격리/재시작/자원 시험, 실제 fork PR의 시크릿 부재와 gate,
Telegram 송신, 5개 생산자의 사건 도달이 각각 확인돼야 파일럿 시작 가능으로 판정한다.
14일 관찰과 충분한 사건의 효과 평가를 끝내야 파일럿 평가 완료로 표시한다. 실제 운영을
진행하지 못한 단계는 모의 성공으로 대체하지 않고 남은 사람 작업/외부 조건을 구체 기록한다.

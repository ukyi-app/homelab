# 결정 원장 — cronjob-flapping (S-6 후속)

## 범위 결정 (2026-07-30)

`#401`의 자체 감사가 남긴 후속 2건을 사용자에게 제시하고 결정받았다.

**adguard `--retry-all-errors` — 취소.** 원래 동기(단발 DNS 실패가 알림 노이즈를 냄)가 `#401`로
**이미 소멸**했다: 실패 후 다음 주기 성공이 600s에 오는데 `KubeJobFailed`의 `for:`가 900s라 억제가
걸려 for를 채우지 못한다. 남은 이득은 rewrite 수렴 10분 단축뿐이고, 비용은 `--retry-all-errors`가
4xx까지 재시도하게 만들어 리컨실러의 명시적 설계 의도("4xx는 재시도 안 함")와 충돌하는 것이다.
장기 침묵은 하트비트 알림(1800s)이 이미 지킨다. → 하지 않는다.

**S-6 만성 flapping 탐지 — 전체 범위로 구현.** 새 룰 + `failedJobsHistoryLimit` 상향 + 발화 e2e.

## 조사에서 확정된 것

사각지대가 **예상보다 하나 더** 있었다 — 하트비트 임계가 주기의 3배인 것들이다:

| CronJob | 주기 | 하트비트 임계 | 배수 | 50% 교대 시 | 판정 |
|---|---|---|---|---|---|
| `adguard-rewrite-reconciler` | 600s | 1800s | 3배 | 1200s | ❌ 사각지대 |
| `gha-liveness-exporter` | 1800s | 5400s | 3배 | 3600s | ❌ 사각지대 |
| `digest-exporter` | 600s | 900s | 1.5배 | 1200s | ✅ 잡힘 |

**성공 기반 지표로는 원리적으로 못 닫는다**(기각한 대안): 교대 실패에서 `time() - last_success`는
주기가 일정한 톱니파라 임계를 어디 두든 `for:`를 채우는 구간이 없고, 주기 아래로 낮추면 정상 동작에서도
매 주기 발화한다. KSM에 `kube_cronjob_status_last_failed_time`도 없다(메트릭 목록 실측).
⇒ 실패를 **사건으로 세는 것**이 유일한 경로이고, 관측 창은 `failedJobsHistoryLimit`다.

## 구현 중 잡은 자기 결함 2건

둘 다 **뮤테이션이 아니었으면 green으로 통과했을 것**이다.

- **픽스처 결손이 룰 결함으로 오독됨** — `stale_failures` 블록을 삽입하면서 flapping 픽스처의
  `kube_cronjob_status_last_successful_time` 줄이 그 블록으로 밀려났다. 억제식 우변이 빈 벡터가 되어
  L7b가 "억제 회귀(#401 회귀)"라는 **틀린 사유로** red를 냈다. 룰은 멀쩡했다. 디버그 덤프로 `f0`·`f1`
  둘 다 firing 91회인 걸 보고서야 갈렸다(별도 재현 스크립트에서는 pending 1건뿐이었다 — 그 불일치가
  단서였다). 해당 줄에 경고 주석을 남겼다.
- **게이트가 자기가 지킬 대상 2건을 조용히 건너뜀** — `cronjobs()` 열거가 블록 형식 `metadata:` 만
  파싱해 인라인 `metadata: { name: x }`인 `digest-exporter`·`gha-liveness-exporter`를 스킵했다.
  하필 **이 작업이 limit을 올린 바로 그 둘**이다. 고정 바닥값 `-ge 5`는 나머지 6건이 세어져 통과했다.
  뮤테이션 M3(limit을 1로 되돌림)이 게이트 4/4 green으로 실측 폭로했다. → 인라인 형식 지원 +
  **추출 실패는 fail-closed**(continue 금지) + 바닥값을 레포 실측 대조로 교체. S-8과 같은 병이다.

## 이빨 (뮤테이션 실측, 2026-07-30)

| 뮤테이션 | 결과 |
|---|---|
| 룰 임계 `>= 2` → `>= 1` | 하네스 preflight CONTRACT(exit 2) |
| 최근성 창 무력화(3600 → 10년) | **L9 red** |
| `digest-exporter` faillimit 2 → 1 | **관측 가능성 게이트 red** |
| 게이트를 인라인 metadata 미지원으로 되돌림 | **게이트가 자기 스킵을 fail-closed로 잡음** |

네 경우 모두 나머지는 green이다 — 정확히 그 결함만 문다.

## release r1 — 적대적 리뷰 4건 전부 accept (사용자 `as proposed`)

- **R-1 accept** — 창 1h가 문서화된 GHA 교대 패턴을 원리적으로 못 잡았다. `gha-liveness-exporter`는
  주기 1800s라 교대 실패 간격이 **3600s**인데 `< 3600`이 두 번째 실패가 나타나는 바로 그 순간 첫 번째를
  떨궈 count가 2에 **영원히 도달하지 못한다**. 즉 닫겠다고 한 사각지대 2개 중 하나가 그대로 열려 있었다.
  e2e가 실패 간격을 임의값 600s로 합성해 가렸고, 정적 게이트는 `period < window`만 봐서 통과시켰다.
  → 창 **7200s**, 하한을 **`2 × 주기 + for`**로 정의해 게이트가 대상별로 강제. e2e의 실패 간격도
    상수에서 **최장 대상 주기의 2배**(gha-liveness 기준 3600s = 최악 케이스)로 파생.
- **R-2 accept** — 계획서는 "억제가 삼키는 영역만 본다"고 했으나 expr은 해소 여부를 묻지 않았다. 연속
  미해소 실패면 `KubeJobFailed`와 둘 다 발화하고, Alertmanager가 alertname으로 그룹핑하므로 **텔레그램
  알림이 2건** 간다 — 알림 노이즈를 줄이려던 작업이 새 노이즈를 만든다.
  → 세는 대상을 **"실패했다가 복구된"** 실행으로 한정(억제 조건과 동일한 부등식). 이제 두 룰은 같은
    신호 위에서 **정확히 상보적**이다. L10이 연속 미해소에서 중복 통지 부재를 잠근다.
- **R-3 accept** — 계획서가 약속한 "L1~L6에서 flapping 오발화 없음"이 실제로는 없었다(그 레그들이
  `KubeJobFailed`만 질의했다). → L1~L6 전부에 침묵 단언 추가.
  ⚠️ 그런데 **R-2 수정이 이 뮤테이션 대상을 무력화**했다: L5는 해소 1건 + 미해소 1건이라 `owner_name`을
    빼도 세어지는 건 1건뿐이라 여전히 침묵했다(뮤테이션 NO_TEETH). → 같은 ns의 두 CronJob이 **각각
    해소된** 실패를 갖는 L11을 신설해 그룹핑 키를 실제로 잠갔다.
- **R-4 accept** — 게이트 파서가 인용/주석 없는 `kind: CronJob` 줄만 인식했고, 바닥값도 **같은 텍스트
  가정**을 써서 `kind: "CronJob"`이 양쪽에서 동시에 사라졌다. → 텍스트 정규식을 **yq 파싱**으로 교체.
  `CronJob` 문자열로 후보만 좁히고(인용·주석·플로우 전부 포함) 판정은 YAML 파서가 한다.
  (권고는 TS 체커 신설이었으나 yq로 같은 효과를 더 작게 얻는다 — 실측으로 확인.)

### 이빨 (뮤테이션 실측)

| 뮤테이션 | 결과 |
|---|---|
| 창 7200 → 3600 | 게이트 red(`gha-liveness 3600 <= 4500`) **+** e2e preflight CONTRACT(겹침 0s) |
| 해소 조건 제거 | **L10b red**(미해소 상태에 flapping도 발화 = 중복 통지 재현) |

## release r2 — finding 1건 accept (사용자 승인 후 라운드 3 진행)

- **R2-1 accept** (high) — *History cleanup resets the adguard alert before its 15-minute `for` completes.*
  **관측 창이 `failedJobsHistoryLimit`이라는 내 전제가 틀렸다.** 창은 정적이 아니라 **새 실패가 도착할
  때마다 밀린다**. 룰이 "복구된" 실패만 세므로(R-2 수정의 결과), 밀려 들어오는 새 실패는 아직 미해소라
  세어지지 않는다 → 유효 count가 임계 아래로 떨어진다.
  실측 시나리오(adguard: 주기 600s, `for` 900s, limit 2): `F1/S1/F2/S2`로 count=2 → pending 시작 →
  600s 뒤 `F3` 도착 → 컨트롤러가 `F1` 회수 → `F2`만 해소 + `F3` 미해소 → count=1 → **pending 리셋**.
  600s < 900s라 매 주기 반복되어 **영구 무발화** — 이 기능이 닫겠다고 한 최악 케이스가 그대로 열려 있었다.
  → `failedJobsHistoryLimit >= 임계 + 1`(adguard·digest-exporter·gha-liveness-exporter 전부 **3**),
    게이트 부등식을 `>= 임계+1`로 교체, 그리고 **수명주기 레그 L12** 신설.
  ⚠️ L7이 이걸 못 잡은 이유도 정확히 지적당했다 — 해소된 실패 2건을 replay 내내 **고정**으로 유지할 뿐
    `F3` 도착과 컨트롤러 회수를 모델링하지 않았다. L12는 `series_window()`로 Job의 **생성~회수 수명**을
    존재 구간으로 표현해 그 동역학을 재생한다(주기·limit 모두 adguard 매니페스트에서 파생).

### 이빨 (뮤테이션 실측)

| 뮤테이션 | 결과 |
|---|---|
| adguard `failedJobsHistoryLimit` 3 → 2 | **L12 red**(수명주기 재생에서 무성 — 회수가 pending을 리셋) **+** 정적 게이트 red(`limit=2 < 임계+1=3`) |

리뷰가 산술로 예측한 동작을 하네스가 **독립적으로 재현**했다 — 두 경로가 같은 결론에 도달한다.

## release r3 (사용자 승인 예외 라운드)

`verdict: approve` · findings 0 · `ok: true` · plan/HEAD 드리프트 없음.

게이트 스킬은 2라운드가 상한이지만, r2의 단일 finding이 high 등급 정확성 결함(닫겠다고 한 최악
케이스가 그대로 열려 있음)이라 사용자가 명시적으로 3라운드를 승인했다. 재검증 항목은 둘이었다:
① 각 대상의 주기와 `for` 조합에서 보존 여유가 실제로 충분한가, ② `series_window()`의 존재 구간
의미론과 L12의 합성 수명주기가 k8s CronJob 컨트롤러 동작과 충실히 일치하는가. 둘 다 통과했고
새로 들여온 critical/high도 없다. 웨이버 없이 approve로 닫힌다.

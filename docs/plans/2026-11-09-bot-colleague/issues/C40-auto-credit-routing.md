## 목표

스위치가 켜져 있고 현재 계정에 두 방식이 설치돼 있으면, 구독 한도 실패 뒤 같은 일을 API로 잇고 한도가 풀리면 구독으로 돌아온다. 스위치가 꺼져 있으면 지금과 같다.

## 할 일

1. 상태를 나눠 저장한다: 설치된 계정·묶음 revision, 구독 상태(쓸 수 있음, 한도(until·다음 확인 시각), 인증 막힘), API 상태(쓸 수 있음, 결제 막힘, 인증 막힘), 실행마다 고정된 방식·runId·revision. `switchAccount`의 넓은 해제는 재사용하지 않는다.
2. 구독 → API: 구독 실행의 종료가 확인된 한도 실패이고 API가 쓸 수 있는 상태면 한 번의 전이로 구독 한도를 적고 그 일을 API로 다시 넣는다. 두 서버·두 실행 자리가 동시에 보고해도 전이는 한 번이다(scheduler 잠금, epoch 비교).
3. API 막힘(결정 3/6): API 결제·429·인증 실패면 그 API revision을 잠그고 다시 두드리지 않는다. 해제는 관리 진입점의 명시적 동작과 키 교체뿐이다. 구독 복귀 예약은 남긴다.
4. 구독 복귀: 리셋 시각 + 1분(모르면 30분) 뒤 실제 대기 작업 하나로 확인한다. 성공하면 새 실행은 구독, 다시 한도면 다음 확인 시각만 갱신한다. 도는 API 실행은 끝까지 둔다.
5. 세 경로(결정 4/6): 대화, PR 리뷰(구독 경고로 미룬 리뷰는 고를 방식 기준으로 판단), 작업 작성(같은 세션의 새 턴, 턴·시간·도구 예산 합산), 변경 자체 리뷰(즉시 결과, 저장 결과 회수, ACK).
6. 늦게 온 결과는 요청에 저장한 계정·revision·runId로 귀속한다. 옛 계정의 결과가 새 계정의 한도·미룸을 건드리지 않는다.
7. 세션 파일이 없거나 unknown인 작업은 스스로 새로 시작하지 않고 보존·안내한다.
8. 관리 진입점: 자동 사용 켜기·끄기 상태 보기, API 잠금 해제. 봇 실행 수 상한은 만들지 않는다(결정 6/6).

## 완료 조건

- [ ] 한도 경고, 인증 실패, 과부하, unknown, 취소, 비상 정지에서는 API 실행 0건(S1).

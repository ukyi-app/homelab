## 할 일

### 묶음 A: 한도·계정
1. **F-1 (AC-16·22):** 변경 자체 리뷰(`ChangeReviewWorker.execute`와 `WorkerResultSchema`, 저장 결과, 응답 유실 뒤 회수 경로)가 실행기의 `rateLimit`을 버린다. 그래서 결제 멈춤이 일반 한도로 기록돼 30분마다 자동 재개하고, 풀리는 시각이 있는 한도도 30분을 쓴다. 일반 PR 리뷰처럼 `rateLimit`을 `waitForUser`까지 전한다. 게시 서버(먼저 배포)와 작업자(나중)의 strict 스키마 호환을 지킨다(선택 칸, 없으면 지금과 같음). 시험: 실제 자체 리뷰 경로에 billing과 `resetsAt`을 넣어 결제는 하루 뒤에도 재개 0, 한도는 풀리는 시각 1분 전까지 0, 응답 유실 뒤 회수에서도 같다.
2. **F-2 (AC-16·21):** 계정 전환 뒤 도착한 옛 실행(전환 전에 시작)의 멈춤이 `recordPause`로 그대로 기록돼 scheduler를 다시 닫는다. 결제면 재시도 시각이 없어 새 계정이 owner 개입까지 멈춘다. 멈춤 기록에도 전환 경계(`started_at <= switched_at`)를 적용해, 옛 계정의 결제·풀리는 시각을 새 계정의 정지 근거로 쓰지 않고 새 자격으로 곧 다시 돌게 한다(재시도 지연과 방식은 정해 적는다). 새 계정에서 실제로 난 결제 멈춤은 그대로 자동 재개하지 않는다.
3. **F-3 (AC-16·21):** 모델 대기열이 상한(`MODEL_QUEUE_LIMIT` 90)이면 `resumeDue`가 `queueFull`에서 멈추고, 멈춘 작업이 남아 scheduler도 풀리지 않아 대기열도 돌지 않는다. `account use`(`switchAccount`)와 관리 재개도 같은 상한에 막힌다. 이미 접수된 멈춤 작업의 재개는 새 접수와 구분해 상한이 재개를 막지 않게 한다(대기열 상한의 뜻은 유지). 시험: 대기 1 + 대기열 90, 대기 2 + 대기열 89에서 시간 경과·계정 전환으로 사람 개입 없이 풀린다.
4. **F-6 (AC-17, C20 6a의 남은 부분):** 변경 작성의 성공 `snapshot` 응답에 실린 `allowed_warning`이 계정 기록에 남지 않는다(`fetchResult`의 `snapshot` 분기가 관측 자리를 지나지 않는다). 검증된 `snapshot`의 관측도 같은 규칙(전환 경계, scheduler 잠금 아래)으로 적는다. 시험: `snapshot` 경고 → PR 리뷰 claim이 미뤄짐 → 기한 뒤 claim.

### 묶음 B: 제안·공개 범위
5. **F-4 (AC-3·7):** 말로 한 "세션 연결 목록"(`attach_list`)이 `/attach-list`의 본문을 공개 검사 없이 일반 답으로 낸다. 확인 글에서 숨긴 세션 ID(공개 검사에 걸리는 값)가 다시 보인다. 일반 답으로 나가는 목록 본문에 공개 검사를 적용하고 걸리는 ID는 숨기거나 고정 안내로 바꾼다. 다른 읽기 제안(작업 목록·상태, 읽기 템플릿)의 본문도 같은 경로인지 확인해 같은 규칙을 적용한다. '/' 명령의 본인 전용 응답은 그대로 둔다.
6. **F-7 (AC-6·28):** 제안의 `later` 실행(수정 요청, 변경 요청 등)은 제안 확정 커밋 뒤 메모리의 콜백으로 돈다. 그 사이 프로세스가 죽으면 값은 이미 비워졌고 실행 의도가 남지 않아 요청이 사라진다. 확정과 같은 트랜잭션에 실행 의도(와 필요한 입력)를 남기고 재시작 뒤 한 번만 이어 실행하거나, 실패 안내를 남긴다. 멱등 키는 `proposal:<id>`를 쓴다. 값 보존 계약(처리·거절·만료 뒤 비움)은 실행이 끝난 뒤에 지킨다.
7. **F-9 (AC-6, 021 보존 계약):** 만료 정리(`expirePending`)가 새 실행 제안을 저장할 때만 돈다. 버튼을 누르지 않고 새 제안도 없으면 기억 제안의 진술이 `proposals.value`에 기한 없이 남는다. 만료 정리를 게시 서버의 시작과 주기 정리에 잇고, 스위치가 꺼져 있어도 돈다.
8. **F-10 (AC-28):** 대화 지시문의 "할 수 있는 일" 목록(`src/bot-facts.ts` `SPEECH_ACTIONS`)에 변경 PR 수정이 없다. 제안 동작 ID `change_amend`와 실행 처리기는 있다. 목록에 넣고(확인 버튼을 거치는 실행, 대상 PR을 가리키는 방법), 실제 작업자 입력 계약 시험(`worker-contract-v2`)으로 고정한다. 작업자 이미지가 바뀌므로 배포 순서를 최종 답에 적는다.
9. **F-11 (AC-23):** 켜짐에서 outbox에 저장한 미전송 버튼 알림(게시 미리보기 등)이 스위치를 끄고 재시작한 뒤에도 버튼과 "버튼을 눌러 주세요"로 게시된다(누르면 거부된다). 보내기 직전에 지금 스위치를 적용한다: 동료 기능 전용 알림은 보내지 않고, 계속 필요한 미리보기·질문은 버튼을 빼고 '/' 안내로 바꾼다.

### 묶음 D: 자체 고치기 경합
13. **F-8 (AC-31):** 게시 서버 둘이 같은 작성 결과를 읽을 때, 한쪽이 결과 저장·시험·리뷰를 마치고 `startSelfFix`로 같은 `generation`의 `fix_round`를 올린 뒤 다른 쪽의 늦은 저장(`recordChangeNotes`·`recordSnapshot`)이 통과한다. 두 함수는 차례를 보지 않는다. 앞 차례 결과가 새 차례의 결과가 되고, 부모가 `verifying`으로 넘어가 새 작성 job을 찾지 못하거나 증거가 엇갈린다. 결과 수신부터 notes·artifact 저장까지 기대하는 `fix_round`(와 작성 job)를 넘기고 부모 잠금 아래에서 지금 차례와 같을 때만 저장한다. 수정 요청 차례(`amendment_round`)에 같은 구멍이 있는지 함께 본다. 시험(실제 PostgreSQL): 앞 차례 결과를 붙든 채 다른 런타임이 `startSelfFix`까지 간 뒤 풀면 옛 결과가 새 차례의 단계·artifact·notes를 바꾸지 않는다.

### 묶음 E: 묶음 B의 리뷰 후속 (봇 PR #147 Codex 2차 P2 둘, 2026-11-11)
14. 꺼짐 판이 없는 동료 전용 글(실행 확인·키 보기·질문 고르기)이 여러 쪽이면 버튼은 마지막 쪽에만 있다. 스위치를 끈 뒤 보낼 때 마지막 쪽만 막히고 앞 쪽(확인 요청과 기억 내용 일부)은 그대로 게시된다. 같은 `message_key`의 모든 쪽에 차단 판단을 적용한다. 미리보기·변경 질문처럼 꺼짐 판이 있는 글은 지금처럼 모든 쪽을 보내고 마지막 쪽만 안내를 바꾼다. 시험: 1600자 진술의 기억 저장 확인 글을 켜짐으로 저장한 뒤 꺼진 게시자로 보내면 어느 쪽도 게시되지 않는다.
15. 말로 한 기억 검색 결과에는 출처 `conversation:<Discord ID>`가 들어가는데, 이 17~20자리 숫자가 공개 검사(`scanPublicPayload`의 `metadata_sensitive`)에 걸려 진술이 안전해도 결과 전체가 고정 문구로 바뀐다(묶음 B의 F-4 수정이 만든 켜짐 판 회귀). 일반 답으로 나가는 기억 검색 결과는 출처 ID를 먼저 가린 뒤 공개 검사를 건다. `/memory-search`의 본인 전용 응답은 그대로다. 공개 범위 자체(internal 기억을 스레드에 내도 되는지, C24 할 일 1a)는 owner 결정 대기이고 이 할 일이 정하지 않는다. 시험: 대화 출처가 있는 안전한 기억을 말로 검색하면 진술이 보이고 출처 ID는 없다. 공개 검사에 걸리는 진술은 여전히 가려진다.

## 목표

동료 기능 스위치를 켠 운영 봇에서 정해진 시범 시나리오가 실제 Discord·GitHub·Telegram으로 통과하고, owner가 말투 표본을 받아들인다. 끝나면 homelab T35(V1 시범 운영, lead 세션 소유)를 시작할 조건이 갖춰졌다고 lead에 알린다.

이 티켓은 코드를 병합하지 않는다. 스위치를 켜면 봇이 다시 뜨고, 그때부터 멘션 제안·실행 확인·키 버튼·작업 질문 바로 답·게시 버튼·변경 질문 선택지·수정 요청·리뷰 요청과 '/' 없는 안내가 운영에 나간다.

## 할 일

1. 시작 조건 확인: C01~C23과 C25~C31이 모두 병합·배포됐고(작업자 이미지는 C06·C23 sandbox PR, C25 작업자 변경 작성 v2는 C06 이미지), C30의 리뷰 App 설치 범위 변경이 승인·기록돼 있고, 봇 `npm test` 전체와 homelab `bun run ci` 전체가 main에서 통과한다. 실패가 있으면 해당 티켓으로 돌려보낸다.
1a. 스위치를 켜기 전 owner 결정(C14 넘김, 2026-11-10): 말로 한 기억 검색은 명세 §4.3대로 확인 없이 스레드에 일반 글로 올라가 internal 기억도 그대로 보인다('/memory-search'는 본인에게만 보이는 응답). 이대로 둘지, 말로 한 검색만 본인에게만 보이게 하거나 internal을 빼게 할지 받는다. 바꾸기로 하면 C14 자리(`src/proposals.ts` 읽기 줄)를 고치는 티켓을 먼저 낸다. **결정(owner 2026-11-11 "좋아 그렇게해"): 말로 한 검색에서 internal을 뺀다. 수정은 C37.**
2. 사람 승인 뒤 스위치를 켠다(Infisical `RUNTIME_POLICIES`의 동료 스위치, 봇 재기동). 기동 로그에서 정책이 받아들여졌는지 본다. 되돌리는 방법(스위치 끄고 재기동)을 승인 요청에 같이 적는다.
3. 시나리오를 돈다. Discord 조작 경로는 운영 메모(iMac agent-desktop)를 따른다. 각 시나리오의 관측과 결과를 기록한다.
   - 멘션 대화: 대화 채널 부모, 알림 채널 부모(경보 글 아래), 봇이 만들지 않은 스레드, 7일 넘게 쉰 스레드. 스레드 제목, 답장·알림 없음, 대조 표식 작은 글씨.
   - 답장 맥락: 봇 글에 답장, 다른 사람 글에 답장.
   - 읽기 요청: 작업 목록, 작업·변경·리뷰 상태, 기억 검색.
   - 실행 확인으로 작업 시작: 되묻기 글, "할게요"·"아니에요", 처리 뒤 버튼 사라짐, 다시 누르기 거부.
   - 작업 질문 바로 답: 열린 질문 하나, 둘 이상(질문 버튼).
   - 기억 저장·검색·삭제와 "원래 메시지는 7일 뒤에 지워져요" 안내.
   - 세션 연결 키 보기: 본인만 보임, 두 번 보기 거부, 공개 글에 키 없음.
   - 게시 버튼: 미리보기 버튼으로 게시, 새 미리보기 뒤 옛 버튼 거부.
   - 반응 전체: 👀, ⏳, 지우기, 실패 한 줄, `ack_only`의 👍.
   - PR 리뷰 댓글: `homelab-smoke` 저장소 PR에서 심각도·한 문단·"승인·병합 판단이 아니다"·대조 표식, Discord 요약에 모델 문장 없음.
   - 모델 멈춤 발화: 실제 한도를 기다리지 않는 주입 방법을 정해(예: 시험용 멈춤 기록, 정한 방법과 이유를 DECISIONS에 적음) 승인받고, Telegram 운영 알림 2분 안 도착, Discord 자리 비움(상태·💤·한 줄), 재개와 해소 알림을 본다.
   - `rate_limit_event` 실측: 이미지의 Claude CLI 2.1.308 `-p` 구독 모드에서 `resetsAt`·사용률 필드가 오는지 본다. 안 오면 30분 재시도로 동작함을 기록한다.
   - 계정 전환: 구독 → API → 구독. 두 레인 반영 지문, 해제, 실행 env 자격 하나.
   - 게시 전 자체 리뷰 고치기(AC-31): 자체 리뷰가 P0·P1을 내도록 만든 변경 요청에서 봇이 게시 전에 스스로 고친 뒤 미리보기로 가는지 본다(재현이 어려우면 관측 사례를 기다리고 미관측으로 기록).
   - 변경 질문 선택지(AC-25): 진행이 불가능한 질문을 내는 변경 요청으로 질문 글에 선택지 버튼(2~4개)과 "직접 답하기"가 나오는지, 버튼으로 한 번·다음 말로 한 번 답해 작업이 이어지는지, 공개 여부를 묻는 글이 없는지 본다. 가정해서 진행한 변경은 미리보기와 PR 설명에 확인할 것 목록이 있는지 본다. 모델이 언제 가정하고 언제 묻는지 표본을 남긴다.
   - 변경 요청 확인 문구(AC-26): 말로 한 변경 요청의 되묻기가 "<저장소>에 이 변경 PR을 준비할까요?"이고 누르면 접수되는지.
   - 안내 댓글(AC-27): 처음 게시한 봇 PR에서 확인할 것·남은 위험 중 diff 안 위치만 `COMMENT` 리뷰 인라인 댓글로 달리고, diff 밖 항목은 PR 설명에만 있고, 자체 리뷰 전문이 없는지 실제 GitHub 화면으로 본다. 수정 요청 한 차례 뒤에는 diff 밖 항목이 Discord 결과 요약에 있고 PR 설명이 그대로인지 본다.
   - 수정 요청 한 차례(AC-28): 봇 PR에 리뷰 댓글을 단 뒤 Discord에서 수정을 요청해 실행 확인 글("PR #n에 리뷰 댓글 k개를 반영해서 수정 커밋을 올릴까요?"), 같은 브랜치의 fast-forward 수정 커밋, 수정 뒤 안내 댓글, Discord 결과 요약과 owner 호출, 변경 CI 통과를 본다.
   - PR 댓글 경계(AC-29): owner 계정으로 봇 PR에 댓글·리뷰만 달았을 때 아무 수정·작업도 시작되지 않는지, `/homelab-review`는 리뷰만 다시 부르는지.
   - 다른 저장소 리뷰 요청(AC-30): 정책 목록 밖 ukyi-app 저장소 PR 하나를 Discord에서 리뷰 부탁해 확인 버튼 없이 `COMMENT` 리뷰가 달리는지, 그 저장소에 새 커밋을 올려도 자동 리뷰가 생기지 않는지, 조직 밖 PR은 못 한다고 답하는지.
   - 스위치 두 상태: 켠 상태에서 봇 글·신뢰 문맥에 '/' 이름이 없는지 표본으로 본다.
4. 말투 표본: 대화 답, 고정 문구, 리뷰 댓글, 안내 댓글, 변경 질문·확인할 것 표본을 모아 owner에게 보이고 수용 여부를 받는다. 받아들이지 않은 문구는 해당 문구 티켓(C09·C10·C18, 리뷰는 C12, 안내 댓글은 C29, 변경 질문은 C25·C28)으로 돌린다.
5. 발견한 결함은 고치지 않고 해당 티켓 또는 새 티켓 제안으로 lead에 넘긴다. 시범 운영을 막는 결함이 남으면 7번 알림을 하지 않는다.
6. 기록: 봇 `docs/ai-bot/VERIFICATION.md`에 "C24 시범 통합 검증" 절(시나리오별 관측·결과·남은 위험), `docs/ai-bot/DECISIONS.md`에 멈춤 주입 방법 문단, homelab [approvals.md](../../2026-10-17-homelab-rebuild/approvals.md)에 승인 줄. 이 계획 폴더 `README.md`의 C24 상태 줄을 갱신한다.
7. 모두 통과하면 lead 세션에 "C24 완료, homelab T35 시작 조건 충족"을 알린다(기록 위치 포함).

## 목표

`claude -p`와 OpenCode에 올리브용 Console API 키를 넣어 돌렸을 때 실제로 구독 포함 크레딧에서 차감되는지 Console 화면으로 확인한다.

## 알려진 사실

- [확인] 포함 API 크레딧은 대화형 Claude Code에는 쓸 수 없다. Console 키를 넣어도 제외 조건은 그대로다.
- [확인] 직접 실행하는 `claude -p`·Agent SDK에 연결 조직의 Console API 키를 넣으면 대상이다.
- [확인] 포함 크레딧은 연결 조직 공용이고, 다른 구매 잔액이 있으면 이어서 쓴다. 계정 폴더 수만큼 크레딧이 생기지 않는다.
- [미확인] OpenCode의 Anthropic 직접 API 사용이 포함분 대상인지, 실제 화면에서 포함분이 줄어드는지.

## 할 일

1. 관리자가 Console에서 확인한다: 구매 잔액·자동 충전 없음, 후불 청구 경로(영업 계약으로 청구받는 조직) 없음, 올리브 전용 workspace와 지출 한도(default workspace에는 지출 한도를 걸 수 없다), 구독 쪽 Usage credits 꺼짐. 값은 저장소에 적지 않는다.
1-1. 두 계정에 연결된 Console 조직이 서로 다른지 본다. 계정 하나는 Console 조직 하나만 연결할 수 있고 조직 하나는 플랜 하나에서만 크레딧을 받는다는 안내가 있다. 같으면 두 크레딧 후보를 따로 셀 수 없으므로 `accounts.md` §4와 O17을 고친다. 조직 ID는 적지 않고 "다름/같음"만 적는다.
1-2. 계정마다 다음 지급 예정일을 화면에서 확인해 적는다(날짜만 보이면 날짜까지만, 시각을 지어내지 않는다). 크레딧은 달력의 1일이 아니라 구독 결제 주기에 들어온다. O17이 이 값을 장부에 등록한다(B-17).
2. 에이전트가 `claude -p`로 작은 실행 몇 번, OpenCode로 작은 실행 몇 번을 한다(올리브 전용 키, 관리자 개인 config 폴더 아님).
3. 관리자가 Console에서 포함 크레딧 잔액이 줄었는지, 다른 잔액이 쓰였는지 본다.
4. 결과를 "결과" 절에 적는다(됨/안 됨, 화면에서 본 항목 이름만).
5. 결과로 `spec.md` §8.3의 [미확인] 줄과 B-08(실행 도구 배정)을 고친다. OpenCode가 차감 대상이 아니면 B-08의 "막히면"대로 크레딧 작업자를 `claude -p`로 돌리는 안을 관리자에게 묻는다(D-14를 바꾸는 일이다).

### 돌린 조건

- 확인한 날: 2026-11-16. 실행 시간대는 12:22~13:08 KST다. Claude Code 2.1.325, OpenCode v2.1.0, 모델은 모두 `claude-sonnet-5-5`, 헤드리스.
- 자격: 계정마다 올리브 전용 workspace에 묶인 Console API 키 하나. 관리자가 Infisical에 넣었고, 실행은 `infisical run`으로 그 계정의 `ANTHROPIC_API_KEY`만 남긴 환경에서 했다. 같은 폴더의 다른 값(구독 토큰 등)은 실행 전에 지웠다.
- 격리: Claude Code는 `CLAUDE_CONFIG_DIR`과 `HOME`을, OpenCode는 XDG 경로 넷을 실행마다 새 빈 폴더로 돌렸다. OpenCode는 `--standalone`으로 전용 서버를 띄웠다. 관리자 개인 config 폴더는 쓰지 않았다.

- 실행 전에 관리자가 자격 조회의 백업 폴더(`infra/README.md` 2절)가 쓰기 불가인 것을 확인했다. 에이전트는 그 폴더를 볼 권한이 없다.

|---|---|---|---|---|---|
| `claude-sub` | `claude -p` | 12:22~12:28, 4번 시도 3번 성공(아래 멈춘 실행) | 됨 | 됨 | 됨 |
| `claude-sub` | OpenCode | 12:31~12:32, 3번 성공 | 됨 | 됨 | 됨 |

- 세 칸은 모두 [확인, 관리자 화면, 2026-11-16]. 화면은 Console → Billing(앞의 두 칸)과 claude.ai → Settings > Usage(셋째 칸)다. 관리자의 답은 네 번 모두 "다 맞음"이었다.

#### 멈춘 실행 하나

- [확인, 실행 기록] `claude-sub`의 `claude -p` 3회째(12:22:49 KST 시작, 출력이 긴 프롬프트)는 init 사건 한 줄만 낸 채 5분 넘게 다음 사건이 없었다. 재시도 사건(`system/api_retry`)도 없었다. 작업자가 12:28:07 KST에 그 `claude` 프로세스에 SIGINT를 보냈고, 2초 안팎에 끝났다. 마지막 `result`는 `subtype: error_during_execution`, `is_error: true`, 사용량 칸은 모두 0, 종료 코드는 0이었다.
- 원인은 모른다. 같은 프롬프트의 바로 앞(2회째)과 바로 뒤(4회째, 150초 제한을 건 재실행)는 15초 안팎에 정상으로 끝났다.
- [추론] 로컬 사용량 0은 서버가 과금하지 않았다는 증거가 아니다. 이 실행의 과금 여부는 모른다. 관리자의 화면 확인은 네 번의 시도가 다 끝난 뒤였으므로 이 한 번의 차감을 따로 가를 수 없다.
- 감독에 주는 뜻 [추론]: 헤드리스 실행이 사건 없이 멈출 수 있으므로 실행마다 시간 상한을 두고 SIGINT로 끊는다. SIGINT의 종료 코드가 0인 것은 O03의 경우 3과 같다. 끊김은 `result` 사건으로 가린다(`accounts.md` §5).

### 남는 한계

- **화면 확인은 관리자의 답이다.** 에이전트는 Console과 claude.ai에 접속하지 않았다. 숫자를 보지 않고 "줄었다/그대로다/늘지 않았다"만 받았다.
- **`claude` 계정의 구독 사용률 칸은 약한 근거다.** 이 확인 작업을 하던 에이전트 세션 자체가 `claude` 구독으로 돌았다. 관리자는 늘지 않았다고 답했지만, 그 세션의 사용이 같은 막대에 섞이므로 크레딧 실행이 구독을 쓰지 않았다는 독립된 증거는 `claude-sub` 쪽뿐이다.
- **다음 지급 때의 실제 동작은 보지 못했다.** 새 크레딧이 만료일 무렵 실제로 들어오는지, 지급이 늦을 때 어떻게 보이는지는 첫 예정일(2026-11-20, `claude`) 뒤 실제 일로 본다(`accounts.md` §3).
- **멈춘 실행 하나의 과금 여부는 모른다**(위).
- 실행 뒤 백업 폴더에 파일이 생기지 않았는지는 확인하지 못했다. 실행 전 쓰기 불가 확인(관리자)만 있다.
- 포함 크레딧 소진, 지출 한도 응답의 모양은 이 티켓의 범위가 아니다(O04). 이번 실행은 한도나 소진에 닿지 않았다.

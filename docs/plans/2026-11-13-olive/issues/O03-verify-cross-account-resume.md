# O03 검증: 계정·방식을 바꾼 뒤 세션 이어 열기

- 단계: 0 끄기와 검증

## 목표

한 계정의 Claude Code 세션을 끝낸 뒤, 다른 계정(구독 → 구독) 또는 다른 방식(구독 → API 키 `-p`)으로 같은 세션을 `--resume`할 수 있는지 확인한다. 안 되면 인계 문서로 새 세션을 여는 방식을 기본으로 정한다.

## 알려진 사실

- [확인] 실행 중 프로세스의 자격을 밖에서 바꾸는 공식 인터페이스는 없다. 전환은 "입력 정지 → 턴 확정 → 옛 프로세스 종료 확인 → 새 자격으로 resume"이다.
- [확인] `--resume`은 압축 전 전체 대화를 다시 싣지 않고, 중단된 도구를 다시 돌리지 않으며, 백그라운드 실행 상태를 복원하지 않는다.
- [확인] 세션 기록은 config 폴더 아래 프로젝트 경로별로 저장된다. 최신 문서는 절대 기록 경로로 `--resume`도 설명한다(설치본 help에는 없음).
- [미확인] 계정이나 인증 방식을 넘나든 `--resume`을 모델 쪽이 받아들이는지.

## 할 일

1. 올리브 전용 시험 config 폴더 두 개를 만든다. 관리자 개인 계정 폴더를 쓰지 않는다. 자격 값은 관리자가 넣는다.
2. 짧은 대화(모델 호출 몇 번)를 계정 A로 만들고 끝낸다. 종료를 확인한다.
3. 같은 기록을 계정 B(구독)로, 그리고 같은 계정 A의 API 키 `-p`로 각각 이어 연다. 기록 파일을 옮겨야 하면 어떤 파일(기록, 부속 폴더)이 필요한지 적고, 자격·계정 설정은 옮기지 않는다.
3-1. 실행 도구가 바뀌는 전환도 본다(D-15: 하위 에이전트는 크레딧 단계에서 OpenCode, 구독 단계에서 Claude Code). 도구가 다르면 기록을 이어 열 수 없다고 보고, 일 도중에 OpenCode(API 키) → Claude Code(구독)로, 다시 Claude Code → OpenCode로 넘길 때 인계 문서만으로 같은 일이 이어지는지 본다. 넘기기 전의 작업 상태·만든 파일·승인 영수증이 보존되는지, 같은 변경이 두 번 실행되지 않는지 적는다.
3-2. OpenCode 안에서 API 계정이 바뀌는 전환도 본다(크레딧 후보가 `claude-sub` 것 → `claude` 것으로 넘어갈 때). 새 전용 서버에서 인계 문서로 이어지는지 본다.
3-3. 끊긴 턴을 본다. 턴 도중에 끝낸 세션을 이어 열었을 때 끊긴 도구가 다시 돌지 않는지, `CLAUDE_CODE_RESUME_INTERRUPTED_TURN`을 막은 상태에서 확인한다. 헤드리스는 SIGINT로 끝낸 경우와 SIGTERM으로 끝낸 경우를 나눈다.
4. 각 경우의 성공 여부, 이어진 맥락의 범위(앞 대화를 기억하는지), 오류 모양을 적는다. "프로세스가 열렸다"와 "모델이 정상으로 답했다"를 따로 적는다.
5. 결과에 따라 `spec.md` §8.2 4번, `accounts.md` §5, O10·O17의 인계 방식을 고친다. 이어 열기가 안 되는 조합에는 인계 경로의 통과 결과가 있어야 한다. 감독은 여기서 통과한 인계 경로로만 새 세션을 스스로 연다(B-17).

## 검증

- 경계: 실제 모델 호출(최소 횟수). 관리자 개인 세션과 섞지 않는다.
- 잡는 실패: 다른 계정 기록 거부, 맥락 유실, 끊긴 턴의 재실행. 못 잡는 범위: 오래 쓴 세션(압축 뒤)의 resume, 세션 부속 파일과 background 자식이 있는 세션(할 수 있으면 한 번씩 보고, 못 보면 그 조합은 인계 문서를 쓴다).

## 결과

**돌려 본 다섯 경우는 모두 열렸고 모델이 답했다. 구독 ↔ 구독의 이어 열기만 조건부다(앞 계정의 thinking은 넘어가지 않는다). 올리브가 실제로 먼저 겪을 쌍(`claude-work` → `claude-sub`)은 돌리지 못해 남은 일이다.**

### 돌린 조건

- 돌린 날: 2026-11-16. Claude Code 2.1.325, OpenCode v2.1.0, 모델은 모두 `claude-sonnet-5-5`, 헤드리스(`claude -p`, `opencode run`). 실제 모델 호출 18번(구독 13번, API 키 5번)과 가짜 키 2번(401로 끝나 모델 응답 없음).
- 계정: 검증 기록은 계정을 A·B·C로만 적었다. A와 B는 서로 다른 구독 계정이고 조직도 다르다(값을 보지 않고 해시로 비교했다). A는 구독만 쓰는 계정이라 API 키가 없다. C는 API 키만 쓴 세 번째 계정이다. 그래서 "같은 계정의 구독 ↔ API"는 A가 아니라 B로 봤다(할 일 3과 다른 점이다).
- 자격: 구독은 관리자가 시험용 config 폴더 두 개에 `/login`으로 넣었다. API 키는 계정별 `ANTHROPIC_API_KEY`를 이름 하나씩 조회해 스크립트의 셸 변수에만 두고 자식의 환경으로 넘겼다. 실행 기록·세션 기록·OpenCode 상태 폴더·작업 폴더에 키 모양의 문자열이 0개인 것을 확인했다. 관리자 개인 계정 폴더에는 시험 프로젝트가 생기지 않았고, 시험이 띄운 프로세스는 모두 끝났다.
- 아래의 "됨"은 모두 [확인, 2026-11-16에 위 버전으로 돌려 본 것]이다. [추론]은 따로 표시했다. 정확한 명령과 실행 기록은 저장소 밖 검증 기록에 있다.

### 1. 구독 → 구독: 조건부 됨

| 방향 | 프로세스가 열렸나 | 모델이 답했나 | 이어진 맥락 |
|---|---|---|---|
| 대조군 A → A | 열림 | 답함 | 암호 단어, 첫 명령의 파일 이름 |
| A → B(기록 파일만 복사) | 열림(같은 세션 ID) | 답함(`result/success`) | 암호 단어, 파일 이름, 앞 턴에서 계산한 숫자. 모두 도구 없이 기억에서 |
| B → A(기록 파일만 복사) | 열림 | 답함 | 위와 같음 |
| A의 기록을 복사 없이 절대 경로로, B에서(`--fork-session`) | 열림(새 세션 ID) | 답함 | 암호 단어. A쪽 원본 기록은 바뀌지 않았고 새 기록은 B의 폴더에 생겼다 |

조건:

- **앞 계정의 thinking은 넘어가지 않는다.** 두 방향 모두 이어 열 때 경고 사건이 하나 나온다: `Claude can't use thinking from another organization`. 대화 글, 도구 호출, 도구 결과는 그대로 실린다. 경고문은 지워진 것이 아니고 원래 조직으로 다시 열면 쓸 수 있으며, 다음 답이 느려지고 토큰을 더 쓸 수 있다고 한다. 이 시험의 답은 모두 맞았다(계산한 숫자는 보이는 답에 있었다). [추론] thinking 안에만 있던 판단은 이어지지 않는다고 봐야 한다.
- **기록의 소유자 줄은 바뀌지 않는다.** 기록에는 계정·조직 식별자가 든 `session-owner` 줄이 있다. B로 이어 쓴 뒤에도 A의 것만 남았다. 열기를 막지는 않았다.
- **옮길 파일은 기록 하나다.** `<config 폴더>/projects/<project>/<세션 ID>.jsonl`만 같은 `<project>` 이름 아래로 복사하면 열렸다. 자격 파일과 계정 설정 파일은 옮기지 않았다. `--resume <절대 경로>`는 help에 없지만 2.1.325에서 동작했다.
- **부속 폴더는 필수가 아니지만 경로가 박혀 있다.** 큰 도구 출력은 `<세션 ID>/tool-results/`에 따로 저장되고, 기록에는 그 파일의 절대 경로(옛 config 폴더 아래)가 들어 있었다. 옛 폴더를 지우면 전문은 다시 읽을 수 없고 기록 속 미리보기만 남는다. 전문이 필요하면 부속 폴더를 같은 절대 경로에 둬야 한다(이 조합은 돌려 보지 않았다).
- 부작용: 첫 턴의 표식 파일은 끝까지 1줄이었다(이어 연 쪽이 앞 명령을 다시 돌리지 않았다).

검증한 범위: A ↔ B 한 쌍, 2.1.325, 짧은 세션(턴 2~3개, 압축 전), `/login` 자격. 확인한 맥락은 암호 단어·파일 이름·계산값 세 가지다. 승인 영수증이나 남은 예산 같은 일의 상태는 이 경우에서 따로 재지 않았다(기록 전체가 실리므로 대화에 있던 것은 이어진다).

### 2. 구독 ↔ 같은 계정의 API `-p`: 됨

로그인이 없는 config 폴더에 기록 파일만 복사하고 `ANTHROPIC_API_KEY`만 준 상태로 열었다. `system/init`의 `apiKeySource`가 `ANTHROPIC_API_KEY`인 것으로 방식을 확인했다(구독 실행은 `none`).

| 방향 | 프로세스가 열렸나 | 모델이 답했나 | 이어진 맥락 |
|---|---|---|---|
| 구독(B) → API 키(B) | 열림(같은 세션 ID) | 답함 | 암호 단어, 파일 이름, 계산값 |
| API 키(B)로 만든 세션 → 구독(B) | 열림 | 답함 | 위와 같음 |

- 두 방향 모두 thinking 경고가 나오지 않았다. thinking이 실제로 다시 쓰였는지는 재지 않았다(경고가 없었다는 사실만 있다).
- API 키로 만든 기록에는 `session-owner` 줄의 계정 값이 없다.
- 오류 모양(가짜 키로 확인): 프로세스는 열리고 `apiKeySource`도 키로 나오지만, `result`가 `subtype: success`인 채 `is_error: true`, `api_error_status: 401`, 글은 `Invalid API key · Fix external API key`이고 종료 코드는 1이다. **실패한 턴도 기록에 덧붙는다**(29줄 → 43줄). 감독은 `subtype`이 아니라 `is_error`를 봐야 하고, 실패한 시도가 원본 기록을 더럽히지 않게 복사본에서 열어야 한다.

### 3. 끊긴 턴: 됨

도구(시작 표식을 쓰고 60초 쉰 뒤 끝 표식을 쓰는 명령)가 도는 중에 헤드리스 프로세스에 신호를 보냈다. `CLAUDE_CODE_RESUME_INTERRUPTED_TURN`은 환경에 없는 상태다.

| | SIGINT | SIGTERM |
|---|---|---|
| 종료 코드 | **0** | 143 |
| 끝날 때까지 | 1초 | 1초 |
| `result` 사건 | 있음: `subtype: error_during_execution`, `is_error: true`, `terminal_reason: aborted_tools` | 없음 |
| 도구 셸과 자식 | 모두 끝남 | 모두 끝남 |
| 기록에 남은 도구 결과 | "The user doesn't want to proceed with this tool use. The tool use was rejected …" 다음에 `[Request interrupted by user for tool use]` | `Exit code 137` |
| 90초 뒤 표식 | 시작 1줄, 끝 0줄 | 시작 1줄, 끝 0줄 |
| 이어 열기(같은 계정, 무관한 한 줄 프롬프트, Bash 허용) | 열림, 답함, 새 도구 호출 0번, 표식 그대로 | 열림, 답함, 새 도구 호출 0번, 표식 그대로 |
| 이어 열기(계정 B로 넘겨서) | 열림, 답함, 새 도구 호출 0번, 표식 그대로 | 돌리지 않음 |

감독이 알아야 할 것:

- **SIGINT의 종료 코드는 0이다.** 끊긴 것은 종료 코드가 아니라 `result` 사건의 `is_error`와 `subtype`으로 가려야 한다.
- **SIGINT 뒤의 기록은 사실과 다르게 읽힌다.** 명령은 실제로 시작해 부작용 한 줄을 남겼는데, 기록에는 "거절됐다, 실행되지 않았다"는 뜻의 문장이 남는다. 이어받은 모델은 그 명령이 돌지 않았다고 믿을 수 있다. 끊긴 도구의 효과는 기록이 아니라 감독이 본 상태(파일, 영수증)로 판정하고, 모르면 "효과를 모르는 도구"로 넘겨야 한다. SIGTERM의 `Exit code 137`은 "죽었다"는 사실만 전한다.
- 두 신호 모두 도구의 프로세스 트리를 1초 안에 정리했다. 유예 뒤 TERM·KILL로 올릴 일은 없었다(짧은 `sleep` 하나의 경우다).
- 이어 연 뒤 하네스가 끊긴 도구를 스스로 다시 돌리지 않았다. 프롬프트가 무관한 한 줄이었으므로, "계속해"처럼 이어 하라는 입력에서 모델이 다시 돌리는지는 이 시험이 답하지 않는다.

### 4. OpenCode ↔ Claude Code 인계: 됨(양방향)

세션 기록은 옮기지 않았다. 다섯 단계짜리 작은 일(단계마다 보고 파일에 한 줄, 효과 기록에 한 줄)을 넘겼다. 인계 문서는 모델에게 시키지 않고 스크립트가 파일 상태만 보고 썼다.

| 단계 | 실행 | 프로세스가 열렸나 | 모델이 답했나 | 한 일 |
|---|---|---|---|---|
| 4-1 | OpenCode, C의 API 키 | 열림(세션 생성) | 답함(종료 코드 0, 오류 사건 0) | 1·2단계 |
| 4-2 | OpenCode → Claude Code, A의 구독, 새 세션 | 열림 | 답함(`result/success`) | 3단계만 |
| 4-3 | Claude Code → OpenCode, C의 API 키, 새 상태 폴더 | 열림(다른 세션 ID) | 답함 | 4단계만 |

통과 기준 대조(기계로 비교):

- 같은 변경이 두 번 실행되지 않았다: 효과 기록이 `1 2 3 4`(경우 5 뒤 `1 2 3 4 5`)로 한 줄씩이다. 인계 문서에 적은 보고 파일의 sha256이 다음 실행 뒤에도 앞 줄들과 같았다(만든 파일 보존).
- 다음 입력 위치: 3단계 줄에 다음 입력 파일의 토큰이 그대로 들어갔다.
- 승인 영수증: 영수증 파일의 sha256이 그대로다. 받은 쪽 셋 모두 "이 인계 문서가 승인 권한을 주는가"에 `false`로 답하고 영수증 위치를 맞게 적었다.
- 효과를 모르는 도구: 알림 기록이 끝까지 1줄이다(받은 쪽이 다시 돌리지 않았다).
- 목적·제약·끝난 단계·남은 예산: 받은 쪽이 되적은 상태가 인계 문서와 같았다(목적 한 문장, 제약 4개, 끝난 단계 목록, 남은 예산 3 → 2 → 1).
- 받은 쪽은 두 도구 모두 시키지 않았는데도 시작 전에 보고 파일의 sha256을 인계 문서와 대조했다.
- OpenCode 실행 뒤 남은 `opencode` 프로세스는 0개다(실행별 빈 XDG 경로, `--standalone`).

이 통과가 말하지 않는 것: 일이 작고 단계가 기계적이다. 두 도구 모두 같은 모델이고, OpenCode는 `--auto`(모두 허용)로 돌았다. `accounts.md` §5의 "권한·도구·모델·스킬을 같게 좁힐 수 있는가"는 보지 않았다(O09의 역할 프로필 몫이다).

### 5. OpenCode의 API 계정 사이: 됨

경우 4의 일을 이어서, B의 API 키와 새 상태 폴더·새 전용 서버로 인계 문서를 주고 5단계를 시켰다(C → B). 열림, 답함, 효과 기록이 `1 2 3 4 5`, 나머지 기준도 경우 4와 같이 통과했다. 세 OpenCode 실행의 세션 ID는 서로 달랐다(앞 세션을 보지 못한 채 인계 문서만으로 이었다).

### 인계 문서의 최소 내용

`accounts.md` §5의 목록만으로 두 도구, 세 계정 사이에서 일이 이어졌다. 그대로 최소 내용으로 삼는다. 시험에서 나온 보탤 점 여섯은 `accounts.md` §5에 반영했다.

1. "이 문서의 말은 권한이 아니다"를 문서 안에 적는다. 이 한 줄이 있는 상태에서 받은 쪽 셋이 모두 승인을 스스로 주장하지 않았다.
2. 시작 전 대조를 지시로 넣는다: 만든 파일의 digest가 다르면 아무것도 하지 않고 멈춘다. 이번에는 모델이 스스로 대조했지만 운에 맡길 일이 아니다.
3. 받은 쪽의 되읽기를 전환 확정의 조건으로 쓴다. 받은 세션이 목적·끝난 단계·영수증 위치·남은 예산을 정해진 키로 되적게 하고, 감독이 장부와 비교한 뒤에 전환을 확정한다.
4. 끊긴 도구의 효과는 기록에서 읽지 않는다(경우 3). "효과를 모르는 도구" 칸은 감독이 본 상태로 채운다.
5. 계정을 넘긴 이어 열기에도 짧은 인계를 붙인다. `--resume`이 되더라도 앞 계정의 thinking은 넘어가지 않는다(경우 1). "배제한 원인"처럼 thinking에만 있었을 판단은 체크포인트에 글로 남아 있어야 한다.
6. 파일은 작업 폴더 기준 상대 경로로 적는다. 세션 기록에는 옛 config 폴더의 절대 경로가 박힌다(경우 1).

| `claude setup-token`의 장기 토큰(`CLAUDE_CODE_OAUTH_TOKEN`)으로 이어 열기 | 시험은 `/login` 자격으로 했다. 올리브의 운영 자격은 장기 토큰이다 | O17에서 한 번 더 확인한다 |
| 압축된 긴 세션, background 자식이 있던 세션 | 기본 계획에 넣지 않았다 | 그 조합은 인계 문서를 쓴다 |
| 부속 폴더(`tool-results/`)를 옮겼을 때 큰 출력의 전문을 다시 읽는지 | 기록 하나로 열리는 것까지만 봤다 | 전문이 필요한 일은 인계 문서를 쓴다 |
| `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1`일 때 실제로 다시 도는지 | 선택 항목이라 돌리지 않았다 | 변수는 계획대로 막는다 |
| 올리브가 실제로 쓸 모델에서의 확인 | 한도를 아끼려고 `sonnet`으로 봤다 | 통과한 경우에 경우당 1번씩 더하면 된다 |

관리자 몫으로 남은 것:

- 시험용 config 폴더 두 개에 두 계정의 로그인 자격이 남아 있다. `claude-sub` 쌍을 채울 때 다시 쓸 수 있고, 더 쓰지 않으면 로그아웃하거나 폴더를 지운다.
- 자격 조회가 암호화된 백업 파일을 남겼을 수 있다(`infra/README.md` 2절의 함정). 검증 작업자는 그 폴더를 볼 권한이 없어 확인하지 못했다.
- 시험에 쓴 API 키가 올리브 전용 workspace의 키인지는 관리자의 말에 따랐고 따로 확인하지 않았다(O05의 몫).

   - 연결의 방향(D-55): 실행기(세션 실행기 포함)가 감독에 인증된 연결 하나를 먼저 열어 유지하고, 감독은 그 연결 위로 지시와 자격을 보낸다. 실행기는 감독용 포트를 열지 않는다. 그래서 옛 봇의 작업자 서버 구조(감독 쪽이 실행기에 붙는 방식)는 그대로 가져오지 않는다. 연결 위의 전송 계약(전달 지연의 상한, 연결이 없을 때의 상태, 다시 붙은 뒤 같은 실행의 조회, 영수증 재전송, 시한 지난 지시 거절)은 이 티켓의 계약 코드가 정한다. 연결이 끊겼다고 같은 작업을 새 실행으로 다시 보내지 않는다(`supervisor.md` §3의 4).
   - 내부 인증(D-58, `supervisor.md` §9.2): mTLS와 효과별 Ed25519 서명이고, 인증서는 클러스터의 cert-manager에 올리브 전용 발급 기관을 두어 낸다. 발급 기관 키의 보관 자리, 인증서의 수명, 교체 절차, 인증서 신원과 역할을 잇는 규칙은 이 티켓이 안을 내고 배포 PR에서 관리자가 본다. Bun 1.4.4 로컬 실측(2026-11-18, 자체 서명 인증서와 `127.0.0.1`)에서 나온 것 [확인]: 상대 인증서 요구와 거절, 상대 신원(SAN, 지문) 읽기, TLS 1.3 강제는 `node:tls`·`node:http2`·`Bun.listen`에서 됐고 `Bun.serve`(HTTP·WebSocket 서버)는 상대 인증서를 읽지 못했다. 그래서 감독 서버는 `Bun.serve`의 WebSocket이 아니라 `node:tls` 계열 위에 자체 메시지 틀을 얹는다. `node:tls`의 `setSecureContext`로 바꾼 인증서는 새 연결부터 적용되고 이미 맺은 연결은 끊기지 않으므로 재연결 규칙이 따로 필요하다. Ed25519의 키 만들기·서명·검증·PEM 읽기는 됐다. [확인, cert-manager 공식 문서] 발급한 인증서는 자동 갱신되지만 발급 기관 자체는 자동으로 교체되지 않으므로 만료 감시와 수동 교체 절차를 만든다. [미확인] 클러스터 안 cert-manager의 실제 발급, Secret 볼륨의 파일이 바뀌는 시점, Ed25519 키를 쓰는 TLS 인증서는 재지 않았다.

2. 역할 표: 진단, 격리 읽기, 코드 작성, PR 리뷰, 기억 정리. 역할마다 고정 프로필(실행 도구, 모델, 자격, 네트워크, 필수 스킬, 시간·토큰 상한). 임의 명령·이미지·볼륨을 받는 API는 만들지 않는다.
   - 배포 대상과 계약 역할(D-64, `supervisor.md` §1.1): 배포 대상 ID `reader`, 네임스페이스 `olive-reader`, 그 안의 Deployment 이름 `executor`는 그대로 두고, 대상 목록 한 곳에 그 대상이 맡을 수 있는 역할을 적는다. 실행기 한 개와 그 서명 키에는 역할 하나만 준다. 처음에는 격리 읽기(`isolated_reader`)만 등록하고, PR 리뷰(`pr_review`)는 별도 실행기를 승인하기 전까지 배정하지 않는다. 같은 자리의 실행기가 다른 역할을 주장하면 거절한다. 칸의 모양과 대조하는 자리(차트, CI, 감독)는 정하지 않았다.

   - PID 상한은 유예다: 노드의 kubelet 설정이라 다른 앱 파드에도 걸리므로 이 티켓에서 걸지 않는다. 시험 클러스터와 시범 운영의 실제 숫자를 본 뒤 별도 호스트 PR로 정한다. 그때까지 이 항목과 `supervisor.md` §12의 PID 항목은 완료로 세지 않는다.

6. 켜고 끄기와 비상 정지(D-21, D-38, D-39, `supervisor.md` §7). 걸기·풀기는 `homelab` CLI 전용이다. Discord 문구로 거는 길은 만들지 않는다.
   - 켜고 끄는 값: 실행 Deployment(감독, 세션, 진단, 읽기·리뷰, 작성)의 Git replicas는 0이고, 켜고 끄기는 CLI가 한다. 그 칸의 Argo CD 예외(`ignoreDifferences` + `RespectIgnoreDifferences=true`)는 실행 Deployment 전부에 있지 않다. 정지 대상과 예외 목록은 같은 집합이 아니다: 세션은 아직 선언한 곳이 없고, 작성의 예외는 sandbox Application에 들어가며 O13의 몫이다(`supervisor.md` §7.3). 이 예외는 Argo CD가 읽은 라이브 값을 다시 쓰는 것이라 [확인] CLI만 쓰는 칸이 아니다.
   - 순서: CLI가 현관에 정지를 접수(새 입력·게시·승인 닫음) → 실행 네임스페이스마다 자물쇠("파드 0개" ResourceQuota, Git 밖)를 먼저 건다 → 현관과 감독이 권한을 폐기 → 감독이 실행기에 종료를 지시(감독이 죽어 있으면 건너뜀) → CLI가 실행 Deployment를 0으로(강제 삭제 없음) → 자물쇠를 건 채 replicas를 지켜보며 1로 돌아오면 바로 다시 내리고, 진행 중인 동기화가 끝나거나 정한 상한이 지나면 0을 마지막으로 확인(상한을 넘기면 "차단됨, replicas 미확정"으로 보고, 상한 값은 이 티켓이 정한다) → 소멸 확인 → 접수·차단·실제 소멸을 따로 보고.
   - 소멸 확인은 CLI가 한다: 기본은 Kubernetes에서 실행 파드 0개·강제 삭제 아님·자물쇠 걸림("정지됨(노드 미확인)"), NUC에서는 그 파드들의 cgroup이 비었는지 sudo 없이 더 읽고("정지 완료(노드 확인)"), `--deep`은 sudo로 컨테이너 런타임 목록을 대조한다. hc의 종료 표시와 감독의 보고는 증거가 아니다. 어느 결과든 닫힌 채 둔다.
   - 공통부 어댑터(homelab #1321, 2026-11-18 01:10 병합, 병합 커밋 `ea4bf8a0`): Deployment replicas 쓰기(0과 1만, 강제 삭제 argv 없음), 자물쇠(파드 0개 ResourceQuota) 걸기·풀기·읽기, replicas 지켜보기, Argo CD Application의 동기화 진행 읽기, 실행 파드 목록, 노드에서 파드 cgroup 읽기가 들어갔다. 부르는 명령(`homelab olive`)은 아직 없어 병합만으로는 클러스터에 쓰지 않는다.

   - CI 정책 검사 [확인, 2026-11-18]: homelab #1326을 14:27에 병합했다(병합 커밋 `e290c246`). 실행 대상 자료(`platform/olive/targets.yaml`)와 실제 선언의 일치(Git replicas 0, 대상과 소유 Application, replicas 예외의 정확한 모양, 대상은 모두 정지 포함)와 실행 네임스페이스의 격리를 CI가 본다. `worker-task`의 Git replicas는 0만 받는다. 아직 없는 것은 CLI 대상 목록과의 일치 검사뿐이다(CLI의 올리브 명령이 아직 없다).
   - 올리브를 걷어낼 때는 CLI로 정지한 뒤 PR을 올린다(root에서 구성 요소를 끄면 Application만 지워지고 Deployment가 남는다 [확인]).
   - 시험 클러스터에서 돌려 볼 것은 `supervisor.md` §12의 O09 줄이다. 한도가 기대대로 막지 않으면 관리자에게 다시 묻는다(차선은 admission 정책).
7. 감독 자신의 상태 지표(살아 있음, 대기열, 비상 정지, 작업자 수)를 내보낸다. 올리브 자신에 대한 새 경보 목록 안을 O16과 함께 낸다.
8. 계정 선택은 이 티켓에서 자리만 만든다(지금 계정 하나 고정). 순서·전환은 O17.
9. 감독 장부와 재시작 복원(`supervisor.md` §8), 현관과의 계약(§9.1, O08과 함께 버전을 붙여 정한다), `homelab olive` 명령(§10)을 만든다. 자원 배분과 실행 감시 숫자는 B-16의 기본값(관리자 미확정)에서 출발한다. 장부 저장 방식(D-56), 내부 인증(D-58), CLI 종료 코드의 규칙(D-61)은 관리자가 정했다.
   - `status`가 감독을 읽는 길(D-60, `supervisor.md` §9.1·§10): 감독 파드의 고정 관리 진입점을 관리자의 Kubernetes 인증으로 `kubectl exec`해 읽는다. 현관이 꺼져 있어도 상태를 본다. exec는 쓰기로 분류돼 감독 줄은 `--apply`를 붙여야 나오고, 정지 여부·replicas·자물쇠 줄은 그냥 나온다. D-60은 접근 경로를 정했고, homelab #1329가 병합되어 감독의 관리 진입점(`bun src/main/admin.ts status`)은 CLI가 검사하는 `olive-supervisor-status/v1`의 여덟 칸(`schema`, `alive`, `queued`, `running`, `diagnosis`, `stop`, `stopGeneration`, `intakeOpen`)을 돌려줘야 한다(아래 줄). `queue`·`runs`·`watch`의 구체적인 모양은 정하지 않았다.
   - 감독 관리 어댑터 [확인, 2026-11-19]: homelab #1329를 11:09에 병합했다(병합 커밋 `ed9023c0`, D-60의 구현). 감독 Deployment가 소유한 파드 하나에만 `kubectl exec`하고, 정해진 여덟 칸의 응답만 받으며 원문은 밖으로 내지 않는다. 진입점(`bun src/main/admin.ts status`)과 응답 모양(`olive-supervisor-status/v1`)은 이 PR이 낸 안이고 감독 쪽이 이 모양에 맞추게 된다. 파드 대조와 exec 사이에 같은 이름의 파드로 바뀌는 경쟁은 막지 못한다. 이 어댑터를 부르는 `homelab olive` 명령은 homelab #1330으로 리뷰 중이다(아직 병합 전).
   - 종료 코드(D-61, `supervisor.md` §10): `homelab` CLI의 공통 규칙을 따른다(3 = 대기: 정지에서 자물쇠는 걸렸고 파드 0개는 아직 확인 전인 상태 등, 1 실패, 64 사용법). 상태별 숫자의 전체 표는 CLI 명령 작업이 정하고 그 PR에서 관리자가 본다.
   - 감독 장부와 재시작 복원기 [확인, 2026-11-19]: olive #4를 11:25에 병합했다(병합 커밋 `6a373e9`). 4차 리뷰의 발견 셋을 장부 사본 작업과 세션 계약 작업의 조건으로 넘겼고, 세션의 시작은 닫아 세션 계약 작업으로 넘겼다(머리말의 (가)). 장부를 부르는 코드는 아직 없다. 장부 사본과 사본에서 뜬 장부의 보류는 olive #5로 리뷰 중이다(아직 병합 전).
   - 장부의 저장과 사본(D-56, `supervisor.md` §8): 장부는 SQLite 파일 하나이고 감독만 쓴다. NUC 로컬 볼륨에 두고 하루 한 번 R2로 사본을 보낸다. 사본 만들기와 복원 검증은 이 티켓 안(운영 배포 전)에서 만든다. 작업 단위 둘과 R2 자격 하나가 더 든다. 백업에서 복원한 장부는 옛 시점이라 새 실행을 멈춘 채 관리자가 대조해야 한다. 볼륨이 루트 디스크인지 둘째 SSD인지는 배포 선언 PR에서 관리자가 보고, 사본의 보존 기간은 정하지 않았다.

## 완료 조건

- [ ] 오케스트레이터가 감독 API 밖으로 작업자를 띄울 수 없다.
- [ ] 두 작업을 동시에 요청하면 하나는 대기한다. 상한을 넘지 않는다(AC-09).

- [ ] 실행기가 서명·시한·세대가 틀린 지시와 계약 밖의 명령·이미지를 거절한다.
- [ ] 비상 정지 뒤 실행 파드 0개와 자물쇠가 확인되고, CLI가 접수·차단·실제 소멸을 따로 보고한다. NUC에서는 "정지 완료(노드 확인)", 원격에서는 "정지됨(노드 미확인)"으로 나온다. 감독·현관 재시작과 노드 재부팅 뒤에도 정지가 유지된다(AC-08).
- [ ] 정지 중 Argo CD 동기화가 겹쳐도 실행 파드가 생기지 않고, 현관·관측 중계·원문 정리는 돈다. Git replicas를 1로 바꾼 PR을 CI가 거절한다(AC-29).
- [ ] 켜 둔 상태의 15분 꺼짐과 정지 중 뜬 파드에 알림이 오고, 일부러 건 정지에는 반복 알림이 없다(AC-30).
- [ ] `homelab` CLI로 상태 보기, 켜기, 비상 정지 걸기·확인·풀기가 된다. 감독이 죽은 상태에서도 정지가 걸린다.

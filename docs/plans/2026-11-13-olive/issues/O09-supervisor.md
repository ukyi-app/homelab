## 목표

모델이 아닌 감독이 서명된 지시로 역할별 파드의 실행기에 고정 역할의 작업자만 띄우게 하고, 예산·동시 실행 상한을 집행한다. 감독은 hc도 Kubernetes 쓰기 권한도 쥐지 않는다. 켜고 끄기와 비상 정지는 관리자의 `homelab` CLI가 하고, 정지의 마지막 확인도 CLI가 한다.

## 할 일

0. 저장소 등록(D-18, `spec.md` §4.1): 관리자가 이름을 정한 뒤 `infra/github/app-repos.json`에 넣는 homelab PR을 올리고, 관리자가 Terraform apply와 템플릿 저장소에서 만들기를 한다(외부 변경, `approvals.md`에 기록). `CODEOWNERS`, `AGENTS.md`, Dockerfile의 버전 고정 검사를 봇 저장소 것에서 가져와 맞춘다. `apps/`에는 등록하지 않는다. 이미지는 `platform/` 값에 digest로 고정하고 사람 PR로만 올린다.
1. 배치(D-37, `supervisor.md` §1.1): 감독은 별도 파드(B-02)이고 hc가 없다. 진단, 읽기·리뷰, 작성 작업자는 역할별 파드에 미리 배포한 고정 실행기가 직접 띄운다(hc 터미널 아님). 관리자 개인 hc core·계정 폴더를 마운트하지 않는다. 감독에게 Kubernetes 쓰기 토큰을 주지 않는다. 감독과 모델 파드는 공용 앱 차트가 아니라 전용 `platform/` 차트로 만든다.
   - 감독과 실행기의 계약(`supervisor.md` §9.2): 지시는 세션 시작·종료, 작업 시작·취소, 실행 갱신, 결과 확정뿐이다. 실행기는 서명·받는 쪽·본문 digest·시한·nonce·세대를 대조하고, 명령·이미지·볼륨·argv·환경을 지시에서 받지 않는다. 자격은 그 실행의 하나만 암호화 연결로 넘기고 실행기는 모델 프로세스의 환경에만 넣는다. 실행기는 접수·시작·종료 확인(남은 프로세스 0개)·정리의 영수증을 낸다. 세션 실행기는 O10이 만들고 같은 계약을 쓴다.
2. 역할 표: 진단, 격리 읽기, 코드 작성, PR 리뷰, 기억 정리. 역할마다 고정 프로필(실행 도구, 모델, 자격, 네트워크, 필수 스킬, 시간·토큰 상한). 임의 명령·이미지·볼륨을 받는 API는 만들지 않는다.
3. 작업자 띄우기 API(오케스트레이터용): `start_worker(role, task)`, `worker_status`, `worker_result`, `cancel_worker`. 결과는 모양·크기 검사(1~2천 토큰 목표) 뒤 돌려준다. 원문 로그·사고 과정은 넘기지 않는다.
4. 상한(B-07): 오케스트레이터 1, 작업자 1(나머지는 대기열), 올리브 전체 CPU 4개·메모리 8GB·PID 상한. 시험·빌드는 머신 전체 잠금(같은 inode)을 쓰고 잠금 획득 뒤 전체 시간 제한을 건다.
5. 유휴 호출 끄기(B-09): 관리 설정으로 prompt suggestions·away summary·idle compaction·goal check-in을 끄고 `autoContinueAtUsageLimit=false`. 환경변수 override도 막는다.
6. 켜고 끄기와 비상 정지(D-21, D-38, D-39, `supervisor.md` §7). 걸기·풀기는 `homelab` CLI 전용이다. Discord 문구로 거는 길은 만들지 않는다.
   - 켜고 끄는 값: 실행 Deployment(감독, 세션, 진단, 읽기·리뷰, 작성)의 Git replicas는 0이고 그 칸만 Argo CD 예외(`ignoreDifferences` + `RespectIgnoreDifferences=true`)로 둔다. 켜고 끄기는 CLI가 한다. 이 예외는 Argo CD가 읽은 라이브 값을 다시 쓰는 것이라 [확인] CLI만 쓰는 칸이 아니다.
   - 순서: CLI가 현관에 정지를 접수(새 입력·게시·승인 닫음) → 실행 네임스페이스마다 자물쇠("파드 0개" ResourceQuota, Git 밖)를 먼저 건다 → 현관과 감독이 권한을 폐기 → 감독이 실행기에 종료를 지시(감독이 죽어 있으면 건너뜀) → CLI가 실행 Deployment를 0으로(강제 삭제 없음) → 자물쇠를 건 채 replicas를 지켜보며 1로 돌아오면 바로 다시 내리고, 진행 중인 동기화가 끝나거나 정한 상한이 지나면 0을 마지막으로 확인(상한을 넘기면 "차단됨, replicas 미확정"으로 보고, 상한 값은 이 티켓이 정한다) → 소멸 확인 → 접수·차단·실제 소멸을 따로 보고.
   - 소멸 확인은 CLI가 한다: 기본은 Kubernetes에서 실행 파드 0개·강제 삭제 아님·자물쇠 걸림("정지됨(노드 미확인)"), NUC에서는 그 파드들의 cgroup이 비었는지 sudo 없이 더 읽고("정지 완료(노드 확인)"), `--deep`은 sudo로 컨테이너 런타임 목록을 대조한다. hc의 종료 표시와 감독의 보고는 증거가 아니다. 어느 결과든 닫힌 채 둔다.
   - 풀기: 실행 파드 0개를 확인한 뒤 자물쇠를 지우고, 감독과 실행기를 접수가 닫힌 채 올려 기동 검사를 한 다음 현관의 접수를 마지막에 연다. 옛 카드·세션·실행은 되살리지 않는다.
   - 알림: 켜 둔다고 했는데 15분째 꺼짐, 정지했는데 파드가 떠 있음(즉시)만 알린다. 일부러 한 정지는 시작과 끝에 한 번씩. 감독이 내려가 있어도 나와야 하므로 경보 규칙으로 만든다(Telegram).
   - 딸린 제약(B-16, 기본값(관리자 미확정)): 정지 중에도 떠 있어야 하는 현관·관측 중계·정리 작업·프록시는 실행 네임스페이스 밖에 두거나 한도에서 뺀다. CI에 "실행 Deployment의 Git replicas는 0"과 실행 대상·예외 대상·CLI 대상 목록의 일치 검사를 넣고, 지금 0과 1을 모두 받는 작성 Deployment 조건과 `platform/sandbox/values.yaml`의 켜고 끄는 절차 주석을 고친다. NUC에서 직접 정지를 거는 길을 준비하고 시험한다.
   - 올리브를 걷어낼 때는 CLI로 정지한 뒤 PR을 올린다(root에서 구성 요소를 끄면 Application만 지워지고 Deployment가 남는다 [확인]).
   - 시험 클러스터에서 돌려 볼 것은 `supervisor.md` §12의 O09 줄이다. 한도가 기대대로 막지 않으면 관리자에게 다시 묻는다(차선은 admission 정책).
7. 감독 자신의 상태 지표(살아 있음, 대기열, 비상 정지, 작업자 수)를 내보낸다. 올리브 자신에 대한 새 경보 목록 안을 O16과 함께 낸다.
8. 계정 선택은 이 티켓에서 자리만 만든다(지금 계정 하나 고정). 순서·전환은 O17.
9. 감독 장부와 재시작 복원(`supervisor.md` §8), 현관과의 계약(§9.1, O08과 함께 버전을 붙여 정한다), `homelab olive` 명령(§10)을 만든다. 장부 저장 방식, 내부 인증, 자원 배분, 실행 감시 숫자, CLI 종료 코드는 B-16의 기본값(관리자 미확정)에서 출발한다.

## 완료 조건

- [ ] 오케스트레이터가 감독 API 밖으로 작업자를 띄울 수 없다.
- [ ] 두 작업을 동시에 요청하면 하나는 대기한다. 상한을 넘지 않는다(AC-09).
- [ ] 감독 파드와 작업자 파드에 hc가 없고, 감독에게 Kubernetes 쓰기 권한이 없다(D-37).
- [ ] 실행기가 서명·시한·세대가 틀린 지시와 계약 밖의 명령·이미지를 거절한다.
- [ ] 비상 정지 뒤 실행 파드 0개와 자물쇠가 확인되고, CLI가 접수·차단·실제 소멸을 따로 보고한다. NUC에서는 "정지 완료(노드 확인)", 원격에서는 "정지됨(노드 미확인)"으로 나온다. 감독·현관 재시작과 노드 재부팅 뒤에도 정지가 유지된다(AC-08).
- [ ] 정지 중 Argo CD 동기화가 겹쳐도 실행 파드가 생기지 않고, 현관·관측 중계·원문 정리는 돈다. Git replicas를 1로 바꾼 PR을 CI가 거절한다(AC-29).
- [ ] 켜 둔 상태의 15분 꺼짐과 정지 중 뜬 파드에 알림이 오고, 일부러 건 정지에는 반복 알림이 없다(AC-30).
- [ ] `homelab` CLI로 상태 보기, 켜기, 비상 정지 걸기·확인·풀기가 된다. 감독이 죽은 상태에서도 정지가 걸린다.

## 검증

- 경계: 단위 시험(모델 호출 없음, 가짜 작업자), 시험 클러스터에서 정지와 동기화의 경합, 배포 뒤 운영 확인. 시험은 한 번에 하나.
- 잡는 실패: 고아 프로세스, 상한 초과, 정지 뒤 재개, 동기화가 되살린 replicas, 자물쇠가 막은 정리 작업. 못 잡는 범위: 실제 모델 작업 부하(O21), 실행 중이던 상태가 든 클러스터 백업의 복원(런북이 아직 없다).

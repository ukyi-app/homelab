# O25 검증: 본체를 다른 uid 컨테이너로 분리

## 목표

D-47의 구조(같은 세션 파드 안에서 hc core·holder·세션 실행기는 제어 컨테이너에, 본체는 다른 uid의 본체 컨테이너에, 둘은 고정 터미널 하나를 잇는 중계로만)가 운영 클러스터에서 성립하는지 실측한다. 특히 세션 교체를 Kubernetes의 전체 컨테이너 재시작에 묶었을 때 옛 본체가 살아 있는 동안 새 자격이 나가지 않는지를 본다. 결과로 D-47을 확정하거나 뒤집히는 조건을 적용한다.

## 알려진 사실

- [확인, O02 실측] 같은 컨테이너·같은 uid의 모델·도구 역할은 hc client·holder 소켓, 상태, `/proc`의 다른 프로세스 환경에 모두 닿았다. 같은 파드의 다른 uid 컨테이너는 폴더 권한 때문에 소켓에 연결하지 못했고 `/proc/net/unix`에서 소켓 **이름**만 봤다. 세션 파드에서는 권한 없는 user 네임스페이스를 만들 수 없다. 세션 컨테이너는 `memory.oom.group=1`이라 한 프로그램의 메모리 초과가 같은 컨테이너 전체를 내렸다.
- [확인, Podman 실측 2026-11-16] 같은 Podman 파드(네트워크·IPC·UTS 공유, PID는 나눔)에 제어 컨테이너(uid 10001)와 본체 컨테이너(uid 10002)를 두고, 본체 컨테이너의 PID 1을 연결 하나를 pty에 잇는 `socat` 한 줄로, 제어 쪽 hc 터미널 프로그램을 그 소켓에 붙는 `socat`으로 돌렸다.
  - 가림: 본체 자리에서 hc client·holder 소켓(경로가 본체 파일 시스템에 없어 ENOENT), 상태·설정, `/proc`의 제어 쪽 프로세스 환경·별칭, 신호, `hc run` 탈출이 모두 막혔다. 남은 것은 공유 네트워크다: `/proc/net/unix`에 hc 소켓 이름 둘이 보이고 abstract 소켓과 localhost TCP에는 닿았다. hc core 자체는 TCP·abstract 수신점을 열지 않았다.
  - 수명: 본체 컨테이너가 연결 하나만 받고 끝나게 하면 `hc kill` 한 번에 본체 컨테이너가 통째로 끝났고(`setsid`·`nohup`·TERM 무시·이중 fork 후손 다섯 모두 0개), 다시 뜬 본체 컨테이너는 깨끗했다(두 번 같은 결과). **본체 컨테이너를 이어 쓰면**(연결마다 새 본체, 컨테이너는 그대로) 앞 세션의 남은 프로세스가 다음 세션 본체의 가짜 자격과 세션 ID를 `/proc`에서 읽었다.
  - 위조: 본체가 쓸 수 있는 공유 폴더에서 중계 소켓을 지우고 같은 경로에 자기 리스너를 심자, 제어 쪽의 다음 연결이 그 리스너에 붙었다. 소켓의 inode·ctime 변화는 재시작 때와 똑같아 "본체가 새로 떴다"의 신호로 못 쓴다.
  - 제어 쪽이 `0.0.0.0`에 쥔 건강 포트는 본체가 주소 넷 × 옵션 셋(12조합) 모두 가로채지 못했다. 다만 Podman은 건강 검사로 죽인 컨테이너를 재시작 정책으로 다시 띄우지 않았다.
  - 화면: 크기 변경이 전달되지 않는다(제어 쪽 pty를 바꿔도 본체 쪽은 고정 크기). 고정 크기에서 Claude Code 첫 화면은 정상으로 그려졌다.
  - 자격: 가짜 자격 파일을 본체 컨테이너에만 붙이자 제어 쪽 hc 상태·설정 폴더와 제어 쪽 프로세스의 인자·환경에서 값이 0건이었다.
  - Claude Code 2.1.325는 glibc 이미지(Debian 12)의 본체 자리에서 중계를 거쳐 첫 화면(네트워크 없음 안내)까지 떴다. 쓰기 가능한 `TMPDIR`가 필요했고, `$HOME/.claude.json`, `$HOME/.claude/`, `$TMPDIR/claude-<uid>`에 썼다. musl 이미지에서는 돌지 않았다. 로그인·도구·훅·MCP는 보지 않았다.
- [확인, 운영 클러스터 2026-11-16] 서버와 kubelet은 `v1.36.5+k3s1`, containerd `2.3.4-k3s1.36`이다. 기능 `ContainerRestartRules`와 `RestartAllContainersOnContainerExits`가 켜져 있다(둘 다 BETA). 동작은 재지 않았다.
- [확인, 문서·소스] Kubernetes 1.36에서 컨테이너의 `restartPolicyRules`에 `RestartAllContainers`를 지정하면 정한 종료 코드로 그 컨테이너가 끝날 때 파드의 모든 컨테이너를 끝내고 init 컨테이너부터 다시 띄운다. 파드 UID·네트워크·볼륨은 유지되고, 이 경로는 `preStop`과 종료 유예를 따르지 않는다. kubelet 소스는 살아 있는 대상을 죽이고 런타임에서 지운 뒤 새로 띄우는 순서다. `ContainerRestartRules`가 꺼지면 API가 그 규칙을 떨어뜨린다는 upstream 주석이 있다. emptyDir은 컨테이너 재시작 뒤에도 남는다.
- [미확인] 이 클러스터에서 전체 재시작이 실제로 그 순서로 도는지, 실패 경로(실행기만 단독 재시작, 본체가 TERM 무시, 규칙 누락)에서 어떻게 되는지. 중계를 거친 실제 대화형 Claude Code가 첫 화면 뒤에도 입력·Ctrl-C·끝내기가 맞는지. 파드의 `fsGroup`·보조 그룹이 중계 폴더 권한을 어떻게 만드는지, `/dev/shm` 공유.

## 할 일

실제 자격과 모델 호출 없이, 가짜 표식과 고정 프로그램으로 한 번에 하나씩 한다. 클러스터를 바꾸는 단계(PR 병합, `kubectl exec`, 파드 삭제)는 관리자 승인 뒤에 한다.

1. 시험 차트: 새 차트 `platform/olive-o25`를 만들고 root에 기본 꺼짐(`components.oliveO25.enabled: false`)으로 둔다. 켜고 끄는 순서는 O02와 같다: 켜는 PR 병합 → 시험 → 끄는 PR 병합(Application과 네임스페이스가 함께 지워지는지 확인) → 차트·도구·CI fixture를 치우는 PR. 이미지와 hc는 digest·sha256으로 고정한다.
2. 시험 파드의 모양 [추론, 이 티켓이 정한다]: 전용 시험 네임스페이스에 파드 하나.
   - 일반 init 컨테이너(restartable sidecar가 아님): 제어 쪽에만 붙인 폴더에 새 세대 표식과 한 번 쓰는 시작 허가를 만든다.
   - 제어 컨테이너(uid A): 고정 버전 hc, 실행기 역할의 고정 프로그램, hc 터미널 프로그램으로 띄우는 중계 클라이언트. 회전 때 정한 종료 코드로 끝나며 그 코드에 `RestartAllContainers` 규칙을 건다.
   - 본체 컨테이너(uid B, 제어 쪽과 다른 gid): glibc 이미지에 고정 버전 Claude Code와 중계 서버. PID 1이 중계 서버이고 본체 명령은 이미지·명령줄에 고정한다. 연결 하나만 받고 끝난다.
   - `shareProcessNamespace: false`(기본값), SA 토큰 없음, 비root, 읽기 전용 root, capability 없음, privilege escalation 금지. hostPath·hostPID·hostNetwork 없음. 컨테이너마다 메모리 상한.
   - 중계 폴더: emptyDir 하나. 제어 쪽 소유이고 제어 쪽만 쓴다. 본체에는 읽기 전용으로 붙인다(Unix 소켓 연결은 읽기 전용 볼륨에서도 된다 [확인, 문서·소스]). hc 폴더·자격·상태는 이 볼륨에 넣지 않는다.
   - 가짜 자격은 제어 쪽이 새 세대를 확인한 뒤 중계와 다른 통로로 본체에게만 준다. 통로의 모양은 이 시험에서 고르고 결과에 적는다.
3. 전체 재시작의 순서: 본체 컨테이너에 분리 후손 다섯(`setsid`, `nohup`, TERM 무시, 이중 fork, 그냥 자식)을 둔 채 제어 쪽이 회전 종료 코드로 끝나게 한다. 옛 본체 프로세스가 모두 사라진 뒤에 init과 새 컨테이너가 뜨는지를 노드에서 본다(그 파드 UID의 컨테이너별 cgroup, `containerStatuses`의 `restartCount`·`containerID`·`startedAt`). 파드 UID가 그대로인지, emptyDir에 앞 세대의 파일이 남는지 적는다.
4. 실패 경로에서 자격 0회: 아래마다 옛 본체가 살아 있는 동안 새 가짜 자격이 본체 쪽 어디에도 나타나지 않는지 본다.
   - 본체의 거짓 종료: 본체가 화면에 끝남·`exit 0`·새 세션 ID를 흉내 낸다.
   - 중계만 끊기: 제어 쪽에서 `hc kill`로 중계 클라이언트만 끝낸다.
   - 실행기만 죽이기: 제어 컨테이너만 회전 코드가 아닌 코드로 끝나 단독 재시작한다. 새 실행기는 이미 쓴 시작 허가를 보고 본체에 자격을 주지 않고 전체 재시작을 요청하는 코드로 끝나야 한다 [추론, 반박 검토의 제안].
   - 본체 컨테이너만 재시작, 본체가 TERM을 무시함, 본체가 중계 소켓을 바꿔치기하려 함.
5. 직접 연결: 본체 쪽에서 hc client·holder 소켓의 **정확한 경로**로 원시 `connect()`를 시도한다(경로를 알려 준다). abstract 소켓과 localhost TCP의 수신점 목록을 적고, 제어 쪽이 연 수신점이 있으면 본체에서 붙어 본다. 중계 폴더에 쓰기·지우기를 시도한다.
6. 중계를 거친 대화형: 고정 버전 Claude Code가 자격 없이 첫 화면까지 뜨는지, 입력이 가고 출력이 오는지, Ctrl-C와 끝내기, 고정 크기에서 화면이 깨지지 않는지 본다. `watch`가 읽을 hc 화면에 본체 출력이 보이는지 함께 적는다.
7. 규칙 누락: `RestartAllContainers` 규칙이 빠진 파드(또는 API가 규칙을 떨어뜨린 파드)에서 실행기의 시작 검사가 그것을 알아채고 본체에 자격을 주지 않으며 시작을 거부하는지 본다. 조용히 "규칙 없는 채로 돈다"가 나오면 실패다.
8. 함께 적을 것: 본체 컨테이너의 메모리 초과가 제어 컨테이너를 내리는지, `fsGroup`·보조 그룹이 중계 폴더와 hc 폴더에 만든 권한, `/dev/shm` 공유 여부.
9. 결과를 "결과" 절에 적고, D-47을 확정할지 뒤집히는 조건을 적용할지 안을 낸다. 시험 파드는 되돌린다.

## 검증

- 경계: 운영 클러스터의 임시 시험 파드. 실제 자격과 모델 호출은 없다. NUC 부하를 지켜보며 한 번에 하나. (4)의 "대화형으로 돈다"는 자격 없이 첫 화면까지와 입력·Ctrl-C·끝내기가 이 티켓의 범위이고, 실제 인증 대화(로그인한 세션, 도구 호출, MCP, 훅)는 O10의 인수 시험이다.
- 잡는 실패: 옛 본체가 남은 채 새 세대가 뜸, 새 자격이 옛 본체에 보임, 중계 소켓 바꿔치기로 제어 쪽이 가짜 끝점에 붙음, 본체에서 hc 소켓 연결, 규칙 누락이 조용히 통과함.
- 못 잡는 범위: 실제 인증 대화와 실제 도구 정책(O10·O21), 같은 파드의 공유 네트워크에 둘 실제 수신점의 인증(O09·O10, `spec.md` §5.3), 본체의 적대적 출력을 hc 화면 해석기가 처리하는 위험(공통 위험), 커널 취약점을 통한 탈출, 실제 실행기 코드(이 시험은 고정 시험 프로그램), 계정 전환 때의 세대 교체(O17).

## 목표

원문·요약·지식·감사가 각자의 기한대로 사라지거나 남고, "잊어 줘"가 살아 있는 세션까지 포함해 즉시 지켜진다.

## 할 일

1. 저장 위치: 원문과 요약은 git 밖 올리브 상태 볼륨, 지식은 비공개 저장소(O19), 감사는 현관 DB.
2. 원문 범위: Discord 메시지 사본, CLI 세션 기록과 부속 폴더, 도구 출력, hc 화면·스크롤백 저장, 첨부. 모두 7일 정리 대상.
3. 보존 시계: 요약·인계는 처음 출처 시각을 이어받는다. 섞이면 가장 이른 만료를 따른다.
4. 원문 168시간, 예외 없음(D-22, `spec.md` §9.1.1). 옛 봇의 예외 셋(끝나지 않은 작업, 누락 복구 대기, 확정 전 게시)을 없앤다.
   - 작업 상태(하기로 한 것, 진행 위치, PR 번호, 승인 영수증)를 받는 즉시 원문과 별개의 구조화 기록으로 남긴다. 받은 지 6일이 된 원문에 끝나지 않은 작업이 걸려 있으면 요약으로 옮기는 정리를 먼저 돌린다.
   - 세션: 오케스트레이터 세션을 하루 한 번 안전한 경계에서 새로 열고(O10), 세션마다 전용 설정·기록 폴더를 쓴다. 정리는 폴더째 지운다. `cleanupPeriodDays`는 두 번째 그물로만 건다. hc의 화면·스크롤백이 어디에 얼마나 남는지 확인해 같은 규칙에 넣는다.
   - 다시 읽기: 관리자가 지난 대화를 다시 보라고 말할 때만 현관이 Discord의 그 스레드를 다시 읽는다. 새 입력으로 취급해 그때부터 168시간. 모델이 스스로 부르는 도구로 만들지 않는다.
   - 정리 작업: 올리브·현관과 별개인 CronJob. 지울 권한만 쥔다(원문 볼륨의 삭제, 현관 DB의 원문 칸 비우기). 올리브·현관이 멈춰 있어도 돈다.
   - 만료 즉시 가림: 조회와 세션 주입은 시각 조건으로 기한이 지난 원문을 고르지 않는다.
   - 지표·경보: 기한이 지난 원문의 수, 정리가 마지막으로 성공한 시각. 경보는 Telegram으로만(B-06).
   - 백업(관리자 "그 백업은 ssd 이용하자"): 원문은 R2로 보내지 않고, 백업 사본을 NUC의 두 번째 SSD(`/mnt/bulk`)에 둔다. 정리 작업이 원본과 SSD 사본을 같은 기한에 지운다. SSD 쪽 디렉터리는 삭제 원장과 같은 방식으로 만든다: `host/install.sh`가 마운트를 확인한 뒤에만 만들고, 정적 local PV로 붙이고, 초기화 표식이 없으면 쓰지 않는다(SSD가 빠진 날 루트 디스크의 같은 경로에 쓰는 함정). 삭제 원장 디렉터리와는 나눈다.
   - 현관 DB의 Discord 입력 원문(옛 봇의 원문 칸: events, 질문, 결과, outbox와 CHANGE 원문)이 DB 백업을 따라 R2로 평문으로 나가지 않게 한다. (가) DB 밖 저장소로 옮기고 사본을 SSD에, (나) DB에 두되 날짜별 키로 암호화하고 키를 SSD에만 백업해 7일 뒤 지움. 둘 가운데 안을 내 관리자가 고른다(§5.3). 두 디스크를 함께 잃으면 처리 중 원문도 잃는다는 점을 안에 적는다.
   - 복구 런북(`docs/runbooks-public/restore.md`)에 루트 디스크만 잃었을 때 SSD 사본에서 7일 안의 원문을 되살리는 절차와, 되살린 직후 정리를 한 번 돌리는 순서를 적는다.
5. 학습 흐름(§9.2, D-27): 자동 승격은 없다. 올리브가 쓴 진단 메모·원인·조치 요약은 30일 단에만 두고 "검증 안 된 메모"로 표시해 찾을 때만 준다. 30일이 지나면 조회에서 사라지고 지운다. 오래 남길 후보는 O19가 PR로 묶는다. 오케스트레이터의 auto memory는 끔.
6. 삭제(§9.3): 즉시 조회·학습 제외 → 영향 세션 교체 → 사본 정리 영수증 → 완료 알림. 지울 수 없는 것을 알린다.
7. 삭제 원장: 옛 봇처럼 DB 복원 대상 밖에 두고 시작 때 재적용, 읽을 수 없으면 기억 접근을 닫는다.
8. 감사 1년: 원문·토큰·전체 화면을 감사에 넣지 않는다.

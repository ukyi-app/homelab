- 명세: `spec.md` §9.1(지식 단), §9.2, §9.4, §4.1(저장소 배치), §5.1 D-19·D-27

- 파일 소유: 지식 저장소의 구조(`lessons/`, `runbooks/`, `skills/`, `INDEX.md` 등), 지도 생성기, 일일 알림 작업
- 설계 계약: 기억 조사 2·3·4·14절

## 목표

지도와 장애 색인이 코드로 만들어지고, 관리자가 병합한 지식만 비공개 git에 출처와 함께 쌓이며, 하루 한 번 "오늘 배운 것"이 후보 PR과 함께 짧게 온다.

## 할 일

1. 저장소 준비(D-19). 순서를 지킨다. 조직이 Free인 동안 비공개 저장소에는 ruleset을 걸 수 없어서, 보호 없이 먼저 만들면 그 사이 main이 열려 있다.
   - 조직이 GitHub Team인지 확인한다. `spec.md` B-13대로면 O15 앞에서 이미 올렸다. 아니면 관리자가 여기서 올린다(요금은 그때 요금제 화면에서 확인, 외부 변경이라 `approvals.md`에 적는다).
   - homelab PR로 `infra/github`에 `olive-knowledge`의 규칙을 선언한다: main은 PR로만, 관리자 승인, force push·삭제 금지. `bot/` 아래 브랜치는 올리브의 쓰기 App만 만들고 바꾼다. 그리고 반대 방향도 건다: 쓰기 App이 `bot/` 밖의 브랜치를 만들거나 바꾸면 서버가 거절한다(D-19의 "올리브의 쓰기는 `bot/` 브랜치뿐"). 지금 공개 저장소의 `bot/` 규칙은 앞 방향만 막으므로 그대로 옮기면 안 된다. 규칙 모양은 O06 4-1의 확인 결과를 쓴다. 공개 저장소 집합을 보는 guard 8은 비공개 저장소를 세지 않는다는 것을 확인한다.
   - 관리자가 저장소를 만들고 Terraform apply를 한다. 만든 직후 규칙이 active인지 API로 읽어 확인한다.
2. 구조: 승인된 지식(main)과 후보 브랜치(`bot/` 아래)를 나눈다. 기억 관리기는 GitHub 토큰을 쥐지 않고 현관 writer를 거쳐 후보 브랜치에만 쓴다. 승인 브랜치 직접 push·이력 재작성·서명 키 없음. 이 거부는 서버 규칙이 강제한다.
3. 커밋에 항목 ID·근거 revision·확인 방식·검토 상태를 연결한다. 개인 선호·원문·내부 식별자는 커밋 메시지와 본문에 넣지 않는다.
4. 자동 병합은 없다(D-27, `spec.md` §9.2). 모델이 쓴 글은 후보 브랜치의 PR로만 올라가고 관리자가 병합한다. 하루치 후보를 PR 하나로 묶는다. 병합되지 않은 후보는 30일 뒤 PR을 닫고 브랜치를 지우고, 올리브 쪽 사본(상태 볼륨, 조회)을 지운다. GitHub은 닫힌 PR의 글을 지워 주지 않으므로 그 글은 비공개 저장소에 남는다(`spec.md` §9.2). 그래서 후보 PR에는 병합할 만한 문장만 넣고 진단 메모 원문은 넣지 않는다. 올리브는 닫힌 PR을 읽지 않는다.
4-1. 지도 생성기: `homelab` 저장소에 둔다. 입력은 저장소(앱·데이터 선언, 경보 규칙, 값 파일)와 관측 중계를 거친 클러스터 상태. 출력은 정해진 모양의 목록(앱, 네임스페이스, 데이터 저장소, 경보와 심각도, 값이 있는 파일 위치). 모델을 부르지 않는다. 저장소 revision이 바뀌거나 하루 한 번 다시 만든다. 옛 봇의 `catalog.ts`가 담던 것을 덮는지 대조한다. 비밀 값·tailnet 이름은 담지 않는다.
4-2. 장애 색인은 O16이 만든다(감독이 진단 실행마다 한 줄, 정해진 칸, 자유 글 없음). 이 티켓은 그것을 읽어 "오늘 배운 것"에 그날 더해진 줄을 알리고, 같은 경보가 되풀이되면 오래 남길 후보(원인 패턴)를 PR에 넣는다.
4-3. 30일 메모 조회: 작업자에게 줄 때 "검증 안 된 메모" 표시와 출처·날짜를 붙인다. 세션 시작 때 자동으로 넣지 않는다.
5. 재확인 주기 초깃값: 런북·절차 30일 또는 관련 구성 변경, 선호 90일 또는 철회. `recheck_due`는 최신인 것처럼 쓰지 않고 "오늘 배운 것"에 재확인 후보로 올린다.
6. 오케스트레이터가 새 세션 때 `INDEX.md`(승인된 지식의 짧은 색인)만 읽고, 나머지는 검색 도구로 필요한 것만.
7. 하루 한 번 오는 글(D-33, `discord.md` §6): 매일 08:50(Asia/Seoul)에 옛 브리핑(백업·인증서·예약 작업 상태)과 "오늘 배운 것"(그날의 후보 PR 링크, 지도·장애 색인에서 달라진 것)을 한 글로 보낸다. 관리자가 할 일을 맨 위에 두고, 전할 것이 없는 날은 보내지 않는다. 옛 브리핑의 일정·중복 방지(`briefing.ts`)를 재사용한다.
7-1. 후속(관리자 2026-11-14 "기존 브리핑도 한번 개선할 부분 있는지 찾아서 개선했으면 좋겠음. 일단 이건 후속으로"): 옛 브리핑이 살펴보는 항목과 문구를 읽고 개선할 점을 찾아 관리자에게 안을 낸다(빠진 항목, 쓸모없는 줄, 늦게 알게 되는 것). 결정 뒤 고친다. 현관 공개 검사 거침. 보낼 곳은 O06 결과대로.
7-2. 계정 안내 두 줄(D-40, D-41): 감독이 내는 재료(O17)를 읽어 하루 한 번 오는 글에 "구독 토큰의 만료가 30일 안"과 "계정을 수동으로 골라 둔 상태"를 싣는다. 계정 이름과 날짜는 쓰지 않고 `homelab` CLI를 안내한다(`accounts.md` §8.3). O17이 아직 끝나지 않았으면 재료가 없어 그 줄은 비어 있다. 두 줄이 실제 글에 실리는지는 O21이 확인한다(AC-33, AC-34).
8. git에 잘못 들어간 비밀의 처리 절차(쓰기 동결 → 이력 재작성 → 사본 추적)를 런북으로 적는다. 파괴 명령은 관리자에게 넘긴다.

## 완료 조건

- [ ] 모델이 쓴 글이 관리자 병합 없이 main에 들어가지 않고, 병합 전 후보의 지시문이 어느 세션에도 지시로 들어가지 않는다(AC-25).
- [ ] "오늘 배운 것"이 하루 한 번 공개 검사를 거쳐 온다(AC-18).

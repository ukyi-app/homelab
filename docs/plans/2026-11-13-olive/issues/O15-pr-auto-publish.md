# O15 PR 자동 게시와 보호 경로 확인 카드

- 단계: 3 스스로 일하기
- 상태: 대기 (선행: O06, O08, O13)
- 명세: `spec.md` §11, §11.1(PR을 올릴 수 있는 저장소), §6 불변 조건 4·5, §3(보호 경로), §5.2 B-12·B-13
- Blocked by: O06, O08, O13
- 연결 AC: AC-13, AC-23, AC-24
- 결정(관리자): D-07 "1번으로"(보호 경로만 빼고 스스로 올린다, 보호 경로는 올리기 전에 확인 카드, 병합은 관리자), D-24 "3번으로 생각했어 조직에 있는 모든레포로하면 매번 설치 안해도 되지 않아?"(대상은 조직의 모든 저장소, 쓰기 App을 "모든 저장소"로 설치), D-25 "1"(자기 저장소 `homelab-bot`·`olive`는 못 바꾼다. 서버 규칙이 브랜치 쓰기를 막고 현관이 PR 요청을 거절한다), D-43 "1"(`homelab-app-template`·`homelab-bot-ops`는 PR 대상에서 계속 뺀다. 서버 규칙은 PR 만들기 자체와 읽기를 막지 못한다), D-26 "1"(카드는 24시간 안에 누를 수 있고 누른 뒤 10분 안에 실행)
- 수행: 에이전트 + 사람(조직 Team 올리기, 쓰기 App 설치 범위 변경, Terraform apply)
- 저장소·PR: 봇 저장소 PR(현관 writer·확인 카드), homelab PR(`infra/github`의 `writer_repos`·규칙·guard, 재구축 설계의 쓰기 App 설치 범위 절)
- 파일 소유: 현관의 게시 정책(자동/확인 분기, 대상 저장소), `isProtectedPath`, `infra/github`의 쓰기 App 관련 선언
- 구현 기준: `diagnosis.md`(근거 등급제, PR 본문에 넣을 것, 병합 뒤 확인, 다시 할지와 차단기의 세부)
- 설계 계약: 보안 조사 4.2·6절, O06 결과

## 목표

코드 작성 작업자의 패치가 검증·자체 리뷰를 통과하면, 보호 경로를 건드리지 않는 한 현관이 확인 없이 PR을 올린다. 보호 경로를 건드리면 올리기 전에 확인 카드로 묻는다.

## 할 일

1. 게시 대상(D-24, D-25, D-43, `spec.md` §11.1): 조직의 모든 저장소. 단 `homelab-bot`과 `olive`는 뺀다(D-25). `homelab-app-template`과 `homelab-bot-ops`도 뺀다(D-43). 아래에서 "막는 저장소 넷"은 이 넷이다. 막는 자리는 둘이다: 서버 규칙이 브랜치 쓰기를 막고, PR 요청은 현관 writer의 코드가 거절한다. 서버 규칙은 PR 만들기 자체와 읽기를 막지 못하고, "모든 저장소" 설치에서는 저장소 하나만 설치에서 뺄 수 없다 [확인, `spec.md` §11.1]. 순서를 지킨다.
   - 관리자가 조직을 GitHub Team으로 올린다(B-13). 비공개 저장소에 규칙을 걸 수 있어야 쓰기 App을 "모든 저장소"로 넓힌다. 늦추면 그때까지 설치를 공개 저장소로만 고른다.
   - homelab PR: 출발점은 지금 선언이다. `writer_repos`는 `homelab`과 `homelab-smoke`이고(`bot/` 규칙과 guard 3·4가 여기서 나온다), 실제 App 설치는 `homelab-smoke` 하나다(`homelab`에서는 2026-11-07에 뺐다). `writer_repos`와 `writer_allowed_repos`, guard 3·4의 기대를 "모든 대상 저장소"로 넓힌다. `homelab-bot`·`olive`(D-25)와 `homelab-app-template`·`homelab-bot-ops`(D-43)에는 쓰기 App이 어떤 브랜치도 만들거나 고치거나 지우지 못하게 하는 규칙을 더한다(규칙 모양은 O06 4-1의 결과를 쓴다). O06 4-1에서 되는 것으로 나오면 대상 저장소에도 "App은 `bot/` 밖 브랜치를 못 만든다"를 건다. 재구축 설계의 쓰기 App 설치 범위 결정도 같은 PR에서 고친다. 관리자 승인과 `approvals.md` 기록이 필요한 외부 변경이다.
   - 관리자가 Terraform apply를 하고, 쓰기 App의 설치 범위를 "모든 저장소"로 바꾼다. 바꾼 직후 막는 저장소 넷에 브랜치 만들기·고치기·지우기가 거절되는지 확인한다(AC-23). 서버가 거절하는 것은 여기까지다.
   - 현관 writer: 대상 저장소를 설정으로 받되 막는 저장소 넷을 대상으로 한 요청(브랜치, 커밋, PR, 댓글)은 GitHub을 부르기 전에 코드에서 거절한다. 그 넷의 PR 요청을 막는 자리는 여기뿐이므로 시험으로 고정한다. 토큰도 그 넷으로 좁혀 발급받지 않는다. 게시마다 대상 저장소 하나와 필요한 권한만으로 좁힌 설치 토큰을 발급받는다(O06에서 되는지 확인).
   - O06의 읽기 확인(2026-11-16)에서 나온 것. 위의 "규칙 모양"은 4-1의 C·D 결과가, "좁힌 토큰"은 A·B 결과가 아래에 있다. 새 저장소의 공백: "모든 저장소" 설치는 새 저장소에도 바로 닿지만 저장소별 Terraform 규칙은 apply 전까지 없을 수 있다. "새 저장소 생성 → 보호 확인 → 현관의 게시 허용" 순서와 조직 차원의 기본 보호가 되는지를 이 티켓에서 검토한다. workflows 거절 뒤의 처리: 4-1에서 거절이 확인되면 확인 카드의 승인만으로는 writer가 워크플로 파일을 게시할 수 없다. O06의 제안(관리자 미확정)은 그런 변경을 관리자의 개발 세션으로 넘기고 writer에 workflows 권한을 더하지 않는 것이다. 기존 `bot/` 규칙을 막는 저장소에 그대로 늘리면 관리자의 `bot/` 브랜치 작업도 막힐 수 있다(O06 결과 7절).
   - O06 4-1의 A·B 결과(2026-11-17, `homelab-smoke`, O06 결과 5-1절) [확인, 실측]: 저장소 하나와 contents·pull_requests 쓰기로 좁힌 설치 토큰이 발급되고 `bot/` 브랜치를 만들었으며, 읽기로 줄인 토큰의 같은 쓰기는 403이었다. 그래서 위 "좁힌 토큰"은 실제로 된다. 다른 저장소로 좁힌 토큰의 거절은 못 봤다. workflows 권한이 없는 writer는 워크플로 파일을 Git push로도 REST(Contents API)로도 올리지 못했다. 그래서 확인 카드의 승인만으로는 워크플로 변경을 게시할 수 없고, 그런 변경을 관리자의 개발 세션으로 넘기는 방향(위 O06의 제안, 관리자 미확정)이 실측과 맞는다. "규칙 모양"(C·D)은 다음 줄에 있다. 위 "실제 App 설치는 `homelab-smoke` 하나"는 2026-11-17에 설치의 마지막 변경 시각(2026-11-07 15:21 KST)으로 간접 확인했다(목록 자체는 직접 읽지 못함).
   - O06 4-1의 C·C-PR·D 결과(2026-11-17, `homelab-smoke`, O06 결과 5-2절). 위 "규칙 모양"의 실측 근거다. 이 모양을 운영에 그대로 쓸지와 통과 목록에 무엇을 넣을지는 이 티켓에서 안을 내고 관리자가 정한다(아직 정하지 않았다).
     - 규칙 모양 [확인, 실측]: 저장소 수준 ruleset, 대상 `branch`, 조건 `ref_name.include: ["~ALL"]`, 규칙 종류 `creation`·`update`·`deletion`, 통과 목록은 저장소 관리자 역할 하나(`bypass_mode: always`, writer 없음). 이것이 켜진 동안 writer의 브랜치 만들기·바꾸기·지우기가 `bot/` 이름과 바깥 이름 모두 422로 거절됐고, 관리자 로그인의 같은 쓰기는 됐다(C). 여기에 `exclude: ["refs/heads/bot/**", "refs/heads/bot/**/*"]`를 더하면 writer는 `bot/` 안(한 단계·중첩 이름)에서만 썼고, 대문자 `BOT/`, 접두가 같은 `botx/`, `renovate/`·`deploy/`·`o06/…`는 바깥으로 막혔다(D).
     - 만들기 차단의 응답 [확인]: REST의 ref 만들기는 `422 Reference update failed`라는 규칙을 말하지 않는 일반 문구로 거절됐다(일곱 번 모두). 바꾸기·지우기는 "Repository rule violations found"로 왔다. GitHub의 공개 이슈(`github/rest-api-description#4887`)는 이 일반 문구가 규칙과 무관하게도 날 수 있다고 보고한다. O06은 만들기 차단을 대조(같은 요청이 규칙 전·`bot/` 안에서는 됨, 그 이름에 임시 규칙만 걸림, 거절 뒤 브랜치 없음, 다른 원인 신호 없음)로 판정했다. 그래서 현관은 이 문구를 "규칙에 막힘"으로 단정하면 안 된다 [추론].
     - PR 만들기 [확인, 실측]: 모든 브랜치의 만들기·바꾸기·지우기를 막는 임시 규칙이 켜진 채로도 writer는 이미 있는 두 브랜치 사이에 draft PR을 만들었다(201, `homelab-smoke` #24, 관리자가 닫음). 막는 저장소 넷의 PR 요청을 막는 자리는 현관 writer의 코드뿐이라는 위 전제가 실측과 맞다.
     - 통과 목록에 넣을 App: 통과 목록에 시험 저장소에 설치되지 않은 것으로 보이는 App을 넣었을 때 규칙 만들기가 422로 거절됐고, 관리자 역할 하나로 줄이자 됐다. 그래서 통과 목록에는 그 저장소에 설치된 App만 넣을 수 있는 것으로 보인다 [추론, O06 C 1회차, 거절 사유 원문은 보지 못함]. 통과 목록에 없는 App은 규칙이 켜진 동안 그 범위의 브랜치 쓰기가 막힌다(이번에는 Renovate도 막히는 모양이었다. 실제로 Renovate가 그 사이 쓰려 했는지는 보지 않았다). 운영 규칙을 이 모양으로 만들 때는 그 저장소에서 브랜치를 쓰는 App(Renovate, 배포 App 등)을 통과 목록에 넣어야 한다 [추론]. 다른 App의 정상 동작은 재지 않았다(못 봄).
     - 기존 `bot-branches`와의 관계: 기존 규칙은 "`bot/` 아래는 App만"이라 관리자의 `bot/` 삭제도 막는다 [확인, O06 래퍼 리뷰에서 규칙 정의로 확인. 시험에서 `bot/` 삭제는 모두 writer 토큰으로 했다]. 기존 규칙과 운영용 새 규칙을 함께 두었을 때 관리자의 `bot/` 작업이 어떻게 되는지는 재지 않았다. 위 "기존 `bot/` 규칙을 막는 저장소에 그대로 늘리면 관리자의 `bot/` 브랜치 작업도 막힐 수 있다"는 그대로 남는다.
     - 재지 않은 것: 규칙이 없을 때 writer가 `bot/` 밖에 브랜치를 만들 수 있는지(바깥 시험 브랜치는 관리자가 만들었다), 다른 저장소로 좁힌 토큰의 배제, Git push로 하는 쓰기의 차단(차단 시험은 REST였다), 조직 수준 규칙.
   - 봇 저장소의 필수 검사(관리자 결정 2026-11-16): `homelab-bot` main에 필수 검사 `build / test`(GitHub Actions 출처)를 요구하는 ruleset 선언을 이 티켓의 다른 ruleset 변경과 함께 한다. 배경은 O06 읽기 확인의 빈틈이다: 지금은 필수 검사가 없어 빌드가 실패해도 병합될 수 있다.
   - 자기 코드의 문제: 패치를 만들지 않고 원인·근거·고칠 곳을 Discord로 알린다(O10의 변경 제안 도구가 대상 저장소를 보고 가른다).
2. 분기: 패치의 모든 경로를 `isProtectedPath`로 검사한다. 하나라도 걸리면 확인 카드, 아니면 자동 게시. `homelab`에서는 B-12의 경로(올리브 배포 선언, `infra/`, `tools/ci/`, `tools/deploy-merge/`)를 보호 경로에 더한다. 저장소마다 다른 목록이 필요한지 본다(앱 저장소의 `Dockerfile`, 잠금 파일 등은 안을 내 관리자에게 묻는다).
3. 확인 카드 내용: 동작(PR 게시), 대상 저장소·base, 변경 요약, 보호 경로 목록, 검증·리뷰 결과, "병합하면 Argo CD가 배포합니다". 시간과 무효 조건은 D-26(`spec.md` §11.2): 승인 낱말("올려")을 쓸 수 있는 시간 24시간, 승인한 뒤 10분 안에 실행(D-30: 버튼 없이 말로만), 내용·대상·보호 경로가 바뀌면 즉시 무효, main이 움직인 것만으로는 무효 아님.
4. 게시 직전에 artifact digest·검증 영수증·base를 다시 대조한다(지금 CHANGE 승인 묶음 유지).
5. PR 본문: `/pr` 틀, 공개 검사(F-8 포함). 올리브가 스스로 고치는 PR은 근거, 배제한 원인, 병합 뒤 확인할 것, 되돌리는 법을 담고(D-34), 그럴듯 등급에서 관리자가 "만들어"라고 해 올린 PR은 제목에 가설임을 표시한다. 내부 정책·작업 ID는 비공개 감사에만.
6. writer는 `bot/change/...` 브랜치만 만들고 `force:false`. 병합 경로 없음(O06에서 main 보호 확인).
7. 같은 원인으로 이미 열린 올리브 PR이 있으면 새로 만들지 않고 알린다.

## 완료 조건

- [ ] 보호 경로 패치는 확인 카드 없이 게시되지 않는다. 그 외는 확인 없이 게시된다(AC-13).
- [ ] 어느 PR도 올리브가 병합하지 않는다.
- [ ] 카드 시간과 무효 조건이 D-26대로다: 24시간 안에 "올려"라고 쓰면 게시, 지나면 만료 안내, 승인한 뒤 10분 넘게 밀리면 승인 소멸, 내용이 바뀌면 무효, main이 움직인 것만으로는 유효(AC-24).
- [ ] 쓰기 App의 자격으로 막는 저장소 넷에 브랜치를 만들거나 고치거나 지우려 하면 GitHub이 거절한다. writer는 그 넷을 대상으로 한 PR 요청을 GitHub을 부르기 전에 거절하고, 그 넷으로 좁힌 토큰을 발급받지 않는다(AC-23).
- [ ] 올리브에게 자기 코드를 고쳐 달라고 하면 PR 없이 진단만 온다(AC-23).
- [ ] `homelab`의 올리브 배포 경로를 건드리는 패치는 확인 카드를 거친다(AC-23).

## 검증

- 경계: 봇 저장소 시험(한 번에 하나), 시험 저장소 또는 초안 PR로 실게시 한 번.
- 잡는 실패: 보호 경로 누락, 승인 뒤 바꿔치기. 못 잡는 범위: 관리자가 악성 변경을 병합하는 경우(§13), 현관이 뚫려 App 키로 막는 저장소 넷을 읽거나 그 넷에 PR API를 부르는 경우(서버 규칙은 브랜치 쓰기만 막는다, D-43).

# O15 PR 자동 게시와 보호 경로 확인 카드

- 단계: 3 스스로 일하기
- 상태: 대기 (선행: O06, O08, O13)
- 명세: `spec.md` §11, §11.1(PR을 올릴 수 있는 저장소), §6 불변 조건 4·5, §3(보호 경로), §5.2 B-12·B-13
- Blocked by: O06, O08, O13
- 연결 AC: AC-13, AC-23, AC-24
- 결정(관리자): D-07 "1번으로"(보호 경로만 빼고 스스로 올린다, 보호 경로는 올리기 전에 확인 카드, 병합은 관리자), D-24 "3번으로 생각했어 조직에 있는 모든레포로하면 매번 설치 안해도 되지 않아?"(대상은 조직의 모든 저장소, 쓰기 App을 "모든 저장소"로 설치), D-25 "1"(자기 저장소 `homelab-bot`·`olive`는 못 바꾼다, 서버 규칙으로 막는다), D-26 "1"(카드는 24시간 안에 누를 수 있고 누른 뒤 10분 안에 실행)
- 수행: 에이전트 + 사람(조직 Team 올리기, 쓰기 App 설치 범위 변경, Terraform apply)
- 저장소·PR: 봇 저장소 PR(현관 writer·확인 카드), homelab PR(`infra/github`의 `writer_repos`·규칙·guard, 재구축 설계의 쓰기 App 설치 범위 절)
- 파일 소유: 현관의 게시 정책(자동/확인 분기, 대상 저장소), `isProtectedPath`, `infra/github`의 쓰기 App 관련 선언
- 설계 계약: 보안 조사 4.2·6절, O06 결과

## 목표

코드 작성 작업자의 패치가 검증·자체 리뷰를 통과하면, 보호 경로를 건드리지 않는 한 현관이 확인 없이 PR을 올린다. 보호 경로를 건드리면 올리기 전에 확인 카드로 묻는다.

## 할 일

1. 게시 대상(D-24, D-25, B-14, `spec.md` §11.1): 조직의 모든 저장소. 단 `homelab-bot`과 `olive`는 뺀다(D-25). `homelab-app-template`과 `homelab-bot-ops`도 뺀다(B-14, 기본값. 관리자가 넣자고 하면 그 둘의 규칙과 아래 목록에서만 뺀다). 아래에서 "막는 저장소 넷"은 이 넷이다. 순서를 지킨다.
   - 관리자가 조직을 GitHub Team으로 올린다(B-13). 비공개 저장소에 규칙을 걸 수 있어야 쓰기 App을 "모든 저장소"로 넓힌다. 늦추면 그때까지 설치를 공개 저장소로만 고른다.
   - homelab PR: 출발점은 지금 선언이다. `writer_repos`는 `homelab`과 `homelab-smoke`이고(`bot/` 규칙과 guard 3·4가 여기서 나온다), 실제 App 설치는 `homelab-smoke` 하나다(`homelab`에서는 2026-11-07에 뺐다). `writer_repos`와 `writer_allowed_repos`, guard 3·4의 기대를 "모든 대상 저장소"로 넓힌다. `homelab-bot`·`olive`(D-25)와 `homelab-app-template`·`homelab-bot-ops`(B-14)에는 쓰기 App이 어떤 브랜치도 만들거나 바꾸지 못하게 하는 규칙을 더한다. O06 4-1에서 되는 것으로 나오면 대상 저장소에도 "App은 `bot/` 밖 브랜치를 못 만든다"를 건다. 재구축 설계의 쓰기 App 설치 범위 결정도 같은 PR에서 고친다. 관리자 승인과 `approvals.md` 기록이 필요한 외부 변경이다.
   - 관리자가 Terraform apply를 하고, 쓰기 App의 설치 범위를 "모든 저장소"로 바꾼다. 바꾼 직후 막는 저장소 넷에 브랜치 만들기가 거절되는지 확인한다(AC-23).
   - 현관 writer: 대상 저장소를 설정으로 받되 막는 저장소 넷은 코드에서도 거절한다. 게시마다 대상 저장소 하나와 필요한 권한만으로 좁힌 설치 토큰을 발급받는다(O06에서 되는지 확인).
   - 자기 코드의 문제: 패치를 만들지 않고 원인·근거·고칠 곳을 Discord로 알린다(O10의 변경 제안 도구가 대상 저장소를 보고 가른다).
2. 분기: 패치의 모든 경로를 `isProtectedPath`로 검사한다. 하나라도 걸리면 확인 카드, 아니면 자동 게시. `homelab`에서는 B-12의 경로(올리브 배포 선언, `infra/`, `tools/ci/`, `tools/deploy-merge/`)를 보호 경로에 더한다. 저장소마다 다른 목록이 필요한지 본다(앱 저장소의 `Dockerfile`, 잠금 파일 등은 안을 내 관리자에게 묻는다).
3. 확인 카드 내용: 동작(PR 게시), 대상 저장소·base, 변경 요약, 보호 경로 목록, 검증·리뷰 결과, "병합하면 Argo CD가 배포합니다". 시간과 무효 조건은 D-26(`spec.md` §11.2): 승인 낱말("올려")을 쓸 수 있는 시간 24시간, 승인한 뒤 10분 안에 실행(D-30: 버튼 없이 말로만), 내용·대상·보호 경로가 바뀌면 즉시 무효, main이 움직인 것만으로는 무효 아님.
4. 게시 직전에 artifact digest·검증 영수증·base를 다시 대조한다(지금 CHANGE 승인 묶음 유지).
5. PR 본문: `/pr` 틀, 공개 검사(F-8 포함). 올리브가 스스로 고치는 PR은 근거, 배제한 원인, 병합 뒤 확인할 것, 되돌리는 법을 담고(D-34), 그럴듯 등급에서 관리자가 "만들어"라고 해 올린 PR은 제목에 가설임을 표시한다. 내부 정책·작업 ID는 비공개 감사에만.
6. writer는 `bot/change/...` 브랜치만 만들고 `force:false`. 병합 경로 없음(O06에서 main 보호 확인).
7. 같은 원인으로 이미 열린 올리브 PR이 있으면 새로 만들지 않고 알린다.

## 완료 조건

- [ ] 보호 경로 패치는 확인 카드 없이 게시되지 않는다. 그 외는 확인 없이 게시된다(AC-13).
- [ ] 어느 PR도 올리브가 병합하지 않는다.
- [ ] 카드 시간과 무효 조건이 D-26대로다: 24시간 안에 "올려"라고 쓰면 게시, 지나면 만료 안내, 승인한 뒤 10분 넘게 밀리면 승인 소멸, 내용이 바뀌면 무효, main이 움직인 것만으로는 유효(AC-24).
- [ ] 쓰기 App의 자격으로 막는 저장소 넷에 브랜치를 만들려 하면 GitHub이 거절하고, writer도 그 넷을 대상으로 받지 않는다(AC-23).
- [ ] 올리브에게 자기 코드를 고쳐 달라고 하면 PR 없이 진단만 온다(AC-23).
- [ ] `homelab`의 올리브 배포 경로를 건드리는 패치는 확인 카드를 거친다(AC-23).

## 검증

- 경계: 봇 저장소 시험(한 번에 하나), 시험 저장소 또는 초안 PR로 실게시 한 번.
- 잡는 실패: 보호 경로 누락, 승인 뒤 바꿔치기. 못 잡는 범위: 관리자가 악성 변경을 병합하는 경우(§13).

# Discord에서 올리브와 일하는 모습

`spec.md`의 결정을 관리자가 실제로 겪는 글과 순서로 풀어 쓴 문서다. 결정의 기준은 `spec.md` §5.1이고, 여기는 그 결정이 Discord에서 어떻게 보이는지를 적는다. 현관(O08)과 오케스트레이터(O10)가 이 문서를 구현 기준으로 삼는다.

- 상태: 관리자와 2026-11-14에 §2~§7을 정했다. §8~§10은 정해진 결정에서 따라 나온 기본값(관리자 미확정)이다.
- 예시 글의 값(시각, 숫자, PR 번호)은 모두 가짜다.

## 1. 옛 동료 봇 명세에서 그대로 가져오는 것

2026-11-09에 관리자가 옛 봇의 대화 방식을 정했다(봇 저장소 `docs/ai-bot/COLLEAGUE_SPEC.md` §3·§4.1·§4.4·§4.5). 올리브도 아래를 그대로 따른다. 관리자가 2026-11-14에 가져오는 데 반대하지 않았다(명시로 다시 고른 것은 아니다).

| 묶음 | 규칙 |
|---|---|
| 부르기 | 허용 채널(대화, 알림)에서 `@`로 부르면 그 메시지에서 스레드가 열린다. 경보 글 아래에서도 부를 수 있다. 올리브가 만들지 않은 스레드, 오래 쉰 스레드에서도 답한다. 올리브 글에 답장하면 그 글을 자료로 보고 답한다 |
| 말투 | 해요체, 결론부터, 짧게. 자기를 "봇"이라고 부르지 않는다. 사람을 가리킬 때 "관리자"라고 쓴다 |
| 반응 | 받으면 👀, 다른 일 뒤에서 기다리면 ⏳, 자리 비움 중이면 💤, 답할 필요가 없는 말에는 글 없이 👍. 답하면 자기가 단 반응을 지운다. 실패하면 반응을 지우고 실패했다는 한 줄을 남긴다 |
| 알림 | 답은 관리자 메시지에 답장으로 달고 알림은 울리지 않는다. 관리자 손이 필요한 글에서만 알림이 울린다 |
| 막혔을 때 | 사소한 갈림길은 가정해서 진행하고 가정한 것을 보여 준다 |
| 자리 비움 | 모델이 멈추면 Discord에는 자리 비움만 보이고 원인·풀리는 시각은 Telegram으로 간다. 멈춘 동안 스레드마다 처음 부를 때 한 번 "지금은 잠깐 자리를 비웠어요. 돌아오면 이어서 할게요."라고 답한다 |
| 스레드 제목 | 관리자 메시지의 앞부분(최대 40자) |
| 관리 기능 | 계정 전환, 비상 정지 걸기·풀기, 자동 진단 끄기, 권한 변경은 Discord에서 받지 않고 `homelab` CLI를 안내한다(D-09, D-21, D-28) |

가져오지 않는 것: '/' 명령(D-02), 실행 확인 버튼과 게시 승인 버튼(D-29, D-30), 세션 연결 키. 옛 기능을 남길지는 O07의 표가 가른다.

## 2. 말로 부탁하기(D-29)

- 변경을 부탁하면 올리브는 무엇을 할지 한 줄로 말하고 바로 진행한다. 되묻고 기다리지 않는다.
- 잘못 알아들었으면 관리자가 "아니"라고 하면 멈춘다.
- 뜻이 여러 갈래로 읽히면 번호를 붙인 선택지를 글로 묻는다. 관리자는 "1번"처럼 말로 답한다. 선택지에 버튼을 쓰지 않는다.

> 관리자: @올리브 adguard 메모리 상한 좀 올려 줘
>
> 올리브: AdGuard 메모리 상한을 250Mi에서 384Mi로 올리는 PR을 준비할게요.

> 관리자: @올리브 백업 주기 줄여 줘
>
> 올리브: 어느 백업을 말씀하시는지 골라 주세요.
> 1. Postgres 기본 백업(지금 하루 한 번)
> 2. WAL 보관 주기
>
> 관리자: 1번

## 3. 확인 카드(D-07, D-26, D-30)

보호 경로를 건드리는 PR을 올리기 전에만 뜬다. 버튼이 없다.

> 올리브: 이 변경은 `infra/github/rulesets.tf`를 건드려요. PR로 올려도 될까요?
> - 대상: `ukyi-app/homelab`
> - 바뀌는 것: 지식 저장소의 main 규칙 선언 추가(파일 2개)
> - 검증: `bun run ci` 통과
> - 병합하면 관리자가 Terraform apply를 해야 적용돼요.
>
> 올리려면 `올려`, 그만두려면 `취소`라고 써 주세요. 24시간 뒤에 만료돼요.
>
> 관리자: 올려
>
> 올리브(카드 글을 고침): 올렸어요, PR #1300.

- 메시지 전체가 `올려`면 승인, `취소`면 거절이다. 현관의 코드가 글자를 대조한다. 모델이 해석하지 않는다.
- 그 스레드에 대기 중인 카드가 하나면 그냥 쓴다. 둘 이상이면 그 카드에 답장으로 단다. 답장 없이 쓰면 현관이 어느 카드인지 번호로 묻는다.
- 다른 말이 붙으면("올려 근데 이 파일은 빼고") 승인이 아니라 새 부탁이다.
- "올려줘"·"ㅇㅋ"처럼 비슷한 말에는 현관이 "`올려` 또는 `취소`라고 써 주세요"라고 한 번 알린다.
- 24시간이 지나면 카드 글이 "만료됐어요"로 바뀐다. 올리브가 스스로 다시 띄우지 않는다.

## 4. 경보 진단 보고(D-08, D-28, D-31)

- 자리: 알림 채널의 그 경보 글 아래 스레드.
- 시작할 때: 글을 쓰지 않고 경보 글에 👀만 단다.
- 결과 글은 하나다. 네 줄 안팎으로 결론, 근거 두세 가지, 모르는 것, 다음을 적는다.

> **AdGuard가 23:40부터 5분 동안 죽었고 지금은 돌아왔어요. 메모리 상한에 걸려 재시작된 거예요.**
>
> → 근거: 23:40에 파드가 메모리 부족으로 한 번 재시작됐고, 직전 사용량이 상한 250Mi에 닿아 있었어요.
>
> → 모르는 것: 그 시각에 왜 메모리가 늘었는지는 못 찾았어요.
>
> → 다음: 상한을 384Mi로 올리는 PR을 준비하고 있어요.

- "다음" 줄은 근거 등급(D-34, `diagnosis.md` §5)에 따라 달라진다. 확실이면 "…하는 PR을 준비하고 있어요." 그럴듯이면 "…로 고쳐 볼 수 있어요. 만들까요?"라고 묻고 관리자가 "만들어"라고 하면 제목에 가설임을 표시해 올린다. 모름이면 "원인은 못 찾았어요. 여기까지 봤어요."로 끝낸다. 사람만 할 수 있는 일이면 그 일을 적는다.
- 병합 뒤 정해진 시간에 한 줄이 더 온다: "병합하고 24시간 동안 메모리 부족 재시작이 없었어요."
- 관리자가 "자세히"라고 하면 진단 메모를 풀어 답한다.
- PR이 나오면 같은 스레드에 "PR #번호 올렸어요" 한 줄이 더 온다.
- 알림이 울리는 때: PR을 봐 줘야 할 때, 사람만 할 수 있는 일이 있을 때, 원인을 못 찾았는데 경보가 아직 울리고 있을 때. 저절로 풀렸고 할 일이 없으면 조용히 글만 남긴다. 경보 자체는 Telegram이 이미 알렸다.
- 다시 울렸는데 진단하지 않는 경우(§11.3)에도 한 줄은 남긴다: "또 울렸어요. PR #1300이 병합을 기다리는 중이에요."
- 차단기에 걸리면: "오늘 자동 진단을 다섯 번 해서 더 하지 않았어요. 봐 달라고 하시면 볼게요."

## 5. 오래 걸리는 일의 진행(D-32)

- 시작할 때 무엇을 할지 한 줄을 쓴다(§2의 그 한 줄이다).
- 단계가 바뀌면 새 글을 쓰지 않고 그 글의 둘째 줄을 고친다. 알림은 울리지 않는다.
- 단계 이름은 정해진 것만 쓴다: 원인 확인, 패치 작성, 검증, PR. 모델이 지어내지 않고 감독이 알려 준 단계를 현관이 적는다.
- 끝나면 결과 글이 따로 온다. 상태 줄은 "끝났어요" 또는 "멈췄어요(이유 한 마디)"로 바뀐다.
- 고친 글에도 공개 검사를 건다.

> 올리브: AdGuard 메모리 상한을 384Mi로 올리는 PR을 준비할게요.
> 지금: 검증하는 중 (원인 확인 → 패치 작성 → **검증** → PR)

## 6. 하루 한 번 오는 글(D-33)

- 매일 08:50(Asia/Seoul)에 알림 채널로 글 하나가 온다. 옛 봇의 브리핑 시각을 그대로 쓴다.
- 옛 브리핑(백업, 인증서, 예약 작업 상태)과 "오늘 배운 것"을 한 글에 담는다. 알림은 하루 한 번만 울린다.
- 첫 줄은 관리자가 할 일의 수다. 할 일이 없으면 "오늘은 하실 일이 없어요."로 시작한다.
- 줄의 순서: 배운 것(후보 PR), 기다리는 PR, 밤사이 있었던 일, 살펴본 것. 해당이 없는 줄은 뺀다.
- 전할 것이 하나도 없는 날은 보내지 않는다. "살펴본 것이 모두 정상"만 있는 날도 보내지 않는다.
- 모델이 쓰지 않는 줄(기다리는 PR, 살펴본 것, 밤사이 경보)은 현관과 감독의 기록에서 코드가 만든다. 배운 것의 요약만 모델이 쓰고 공개 검사를 거친다.

> **병합해 주실 것 하나, 봐 주실 것 하나 있어요.**
>
> → 배운 것: 후보 2건을 PR #12로 묶었어요. 병합하시면 기억해요.
>
> → 기다리는 PR: #1300(AdGuard 메모리 상한)이 어제부터 리뷰를 기다려요.
>
> → 밤사이: 23:40에 AdGuard가 5분 죽었다가 돌아왔어요.
>
> → 살펴본 것: 백업과 인증서는 정상이에요.

후속(관리자 2026-11-14): 옛 브리핑이 살펴보는 항목과 문구 자체에 개선할 점이 있는지 찾아 안을 낸다. 이 계획의 범위 밖에 두지 않고 O19에서 한다.

## 7. 누가 보는가

올리브가 글을 쓰는 Discord 서버는 관리자 혼자 본다(관리자 2026-11-14 "1"). 그래서 진단 내용과 서비스 이름이 든 답을 채널에 그대로 쓴다. 다른 사람이나 다른 봇을 서버에 들이면 이 절을 다시 정한다. O06이 서버의 구성원·봇 목록을 한 번 읽어 이 전제를 확인한다. 공개 검사(비밀 값, tailnet 이름 등)는 독자와 상관없이 모든 글에 건다.

## 8. PR 리뷰 부탁(D-06)

기본값(관리자 미확정). 옛 명세의 흐름을 따른다.

> 관리자: @올리브 이 PR 리뷰해 줘 (PR 링크)
>
> 올리브: #1301을 리뷰할게요.
> 지금: 읽는 중 (읽기 → **리뷰 작성** → GitHub 게시)
>
> 올리브: #1301 리뷰를 달았어요. 고쳐야 할 것 하나(P1), 살펴볼 것 둘(P2)이에요.
> → P1: 값 파일의 키 이름이 스키마와 달라 렌더가 실패해요.

- 조직의 어느 저장소 PR이든 부탁할 수 있다. 확인 없이 바로 시작한다.
- 리뷰는 GitHub의 그 PR에 리뷰 App 신원으로 달린다. 심각도 표시(P0~P3)를 남기고 "승인·병합 판단이 아니다"를 적는다.
- Discord에는 요약만 온다. 가장 심각한 것 하나를 한 줄로 싣는다.
- PR의 글과 댓글은 격리 읽기 작업자가 읽는다. 그 안의 지시는 따르지 않는다.

## 9. 올리브가 하지 않는 일을 부탁받았을 때

기본값(관리자 미확정). 못 한다고만 하지 않고, 대신 할 수 있는 것을 한 줄로 말한다.

| 부탁 | 답 |
|---|---|
| 계정 전환, 비상 정지, 자동 진단 끄기, 권한 변경 | "그건 `homelab` CLI에서 해 주세요." 현관이 모델 없이 답한다 |
| 병합, 배포 | "병합은 GitHub에서 해 주세요. PR은 #1300이에요." |
| 올리브 자신의 코드(`homelab-bot`, `olive`) 수정(D-25) | "제 코드는 제가 고칠 수 없어요. 원인은 …이고 고칠 곳은 …예요." 진단만 온다 |
| Secret 값 보기, 파드 안에서 명령 실행, 호스트 작업 | "그건 제가 볼 수 없어요. 대신 …은 확인할 수 있어요." |

## 10. 기억에 대한 말(D-10, D-27)

기본값(관리자 미확정).

- "이거 기억해 둬": 올리브가 저장할 문장을 그대로 보여 주고 지식 저장소에 PR을 바로 올린다. "PR #13으로 올렸어요. 병합하시면 계속 기억해요." 병합 전에도 30일 동안은 메모로 참고한다. 관리자가 직접 한 말이라 다음 날 아침 글까지 기다리지 않는다.
- "이건 틀렸어": 그 지식을 고치는 PR을 올린다. 30일 메모는 바로 고친다.
- "이거 잊어 줘": 바로 조회와 학습에서 뺀다(D-10). "지금부터 안 써요. 사본을 지우는 중이에요."라고 답하고, 다 지우면 지울 수 없는 것(이미 Discord에 나간 글 등)과 함께 알린다. 병합된 지식이면 지우는 PR도 올린다.
- 원문이 지워진 오래된 스레드에서는 앞 내용이 기억나지 않는다고 말한다. 관리자가 다시 보라고 하면 그 스레드를 다시 읽는다(D-22).
